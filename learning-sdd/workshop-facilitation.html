💡 核心理念

“以规格为源”，确保代码与测试始终与设计保持一致。OpenSpec 倡导的新范式：意图 -> 探索 -> 提案 -> 原型 -> 规范 -> 实现 -> 同步 -> 归档。

📦 本期实战案例：促销与优惠券系统

本项目 ecommerce-mini 已具备商品目录、购物车与订单结算等基础功能。本次任务是通过 SDD 流程为其添加“促销与优惠券”的核心能力。

技术栈限制：
  • • 后端: Node.js v20+, 零依赖
  • • 前端: Vue 3 + Tailwind
  • • 存储: 内存 Map / JSON 文件

新需求挑战：

  • 需求 1 优惠券核销：支持在购物车输入优惠券码，校验有效性与门槛。
  • 需求 2 动态计价：结算时自动应用折扣，展示优惠明细。
  • 需求 3 质量要求：核心逻辑 100% 单元测试覆盖。

实战演练 (Execution Workflow)

遵循 OpenSpec v1.5.0 范式
01 20 min

理论导入：AI 协作新范式

从“人写代码”转向“人把关规范”。理解 SDD 如何通过确定性的流程消除需求偏差。

🧠 AI 工作流深度复盘 📘 OpenSpec 用户手册
02 15 min

环境准备：Setup & Check

依据 README.md 完成工具链初始化与环境检查。

# 1. 安装 OpenSpec 命令行工具
npm install -g @fission-ai/openspec@latest
# 2. 为 Trae/Cursor 生成 AI 协作技能
openspec init --tools trae
# 3. 验证基础依赖
node -v # 应 >= v20.19.0
python --version # 应 >= v3.10

Review 要点：

  • 确认 `openspec --version` 能正确返回版本号
  • 确认 `.trae/skills/` 目录下已生成对应的技能定义文件
03 20 min

Explore：意图对齐与方案探索

穿梭点：架构定位

在动工前，让 AI 调查现有 `OrderService` 与 `CartService` 的耦合情况，寻找优惠券逻辑的最佳切入点。

/opsx:explore
"我想在当前系统中加入优惠券功能。请分析 OrderService 的结算流程，建议是在 Cart 中处理优惠还是在 Order 创建时处理？并检查现有的数据模型是否支持扩展优惠金额字段。"
Review 要点： 方案是否破坏了现有的 `ecommerce-mini` 零依赖原则？是否考虑了分（Cents）为单位的精度问题？
04 25 min

Propose & Prototype：提案与原型

穿梭点：视觉对齐

正式发起变更，并要求 AI 生成可交互的 HTML 原型以确认 UI 效果。

/opsx:propose coupon-system
"为系统增加优惠券核销功能。要求：在购物车页面底部增加输入框，支持 SAVE20 (8折) 优惠码；结算页显示 '原价'、'优惠金额' 和 '实付金额'。请先提供一个交互原型。"
Review 要点 (Visual Gating)： 点击“应用优惠券”后，总价是否即时刷新？UI 是否符合“现代扁平化”审美（1px 边框、无阴影）？
05 25 min

Spec：规格审查

穿梭点：规则量化审查

审查并微调 AI 在 Propose 阶段自动生成的 `spec.md`。确保 Gherkin 场景精确覆盖了业务边界，人是最终的质量把关者。

Scenario 示例：

Given 购物车总额为 10000 分
When 输入优惠码 "SAVE20"
Then 实付金额应更新为 8000 分
And 优惠明细应显示 "折扣优惠: 2000 分"
Review 要点： 每个 Requirement 是否都有 Rationale？是否覆盖了“无效优惠码”和“未达门槛”的异常路径？
06 15 min

Plan：规划审查

穿梭点：路径对齐审查

审查 AI 自动生成的 `tasks.md`。确保技术路径与 `spec.md` 中的需求 100% 匹配，特别是数据结构的修改建议。

- [ ] 在 src/domain/types.js 中增加 Coupon 类型定义
- [ ] 修改 src/services/order.js，在 createOrder 中注入优惠计算拦截器
- [ ] 在 __tests__/unit.spec.js 中增加优惠计价的数学准确性测试

Review 要点：

  • 每个 Requirement 是否都有对应的技术 Task？
  • 是否考虑了数据存储（内存 Map / JSON 文件）的更新？
07 30 min

Apply & Harness：实现与质量门禁

穿梭点：确定性交付

执行代码生成，并通过自动化测试验证交付质量。

/opsx:apply
"请按计划实施优惠券功能。完成后，运行 npm test 并提供测试覆盖率报告，确保优惠计算逻辑无死角。"
PASS src/services/order.spec.js
✓ should apply 20% discount for SAVE20 (12ms)
✓ should reject expired coupons (5ms)
08 10 min

Sync & Archive：资产沉淀

将变更同步至主规范，并归档开发记录，确保团队知识库持续演进。

/opsx:sync # 将增量同步到 root specs/
/opsx:archive # 移动到 archive 目录

Review 要点：

  • 确认 `openspec/specs/` 下出现了新的 `promotion-management` 目录
  • 确认 `openspec/changes/` 下的活跃变更已清空
09 20 min

Demo & 复盘总结

展示最终交付的功能，分享在 SDD 流程中“人机协作”的体会，总结 OpenSpec v1.5.0 的核心价值。

成果演示

  • • 购物车输入 SAVE20 后的即时价格变动
  • • 结算生成的订单中包含准确的优惠金额明细
  • • 自动化测试报告与 100% 覆盖率证据

复盘要点

  • • AI 生成 vs 人类审查的效率提升感
  • • Spec 作为“唯一事实来源”在沟通中的作用
  • • 质量门禁 (Harness) 对交付信心的增强
