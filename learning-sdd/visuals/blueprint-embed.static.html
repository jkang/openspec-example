01

极简交付 · Layer 01

Minimalist Delivery / Single Change Pipeline

SPEC-DRIVEN DEVELOPMENT
NON-COMPLEX · LOW GATE

Balance 权衡 · 轻量 ↔ 易用 ↔ 有效

单兵 / 小团队低复杂度变更想法快速验证
轻量 最轻

最低治理，单 Agent 一路到归档，无基线依赖。

易用 最易

上手极快，无 HITL 门禁拖慢，适合快速试错。

有效 最弱

仅靠「验证门禁」兜底；无基线，变更一多就漂移。

何时选它 · 平衡点

零门槛但防线薄弱——验证门禁是唯一护栏。当变更开始跨模块/累积时，该迁往 Layer 02。

警示 · 别踩

不要在这个形态硬塞业务基线：会拖慢"想法→验证"的响应速度（轻量提案 §3.1「最小治理集合」）。

真实案例锚点

epic-account-system（轻量多 Story）epic-sales-dashboard（多 Story 协同）
02

轻量产品 · Layer 02

Lightweight Product / Baseline Guardrail / Multi-Story Loop

COLLABORATIVE SDD
MULTI-STORY · BASE GUARDRAIL

Balance 权衡 · 轻量 ↔ 易用 ↔ 有效

复杂业务逻辑多 Story 循环业务价值对齐
轻量 中

基线只放必选（PRODUCT/ROADMAP/domain/process），service_blueprint、delivery_board 按需增强。

易用 中

原型/Story 各有一道 HITL 确认，认知密度适中；PM 与 Engineer 各管一段。

有效 中强

基线护栏兜住"方向不偏"，多 Story 循环防大爆炸。

何时选它 · 平衡点

用最小治理集合换取方向可控——别把基线一次铺满（轻量提案 §3.1：必需四项 + 按需增强项）。

警示 · 别踩

交互复杂时优先单文件 HTML 原型而非完整前端工程（轻量提案 §3.2「原型形式选择」），控易用性成本。

真实案例锚点

epic-account-system（登入/注册/会话/管理 多 Story）epic-sales-dashboard（概览/排名多 Story）
03

业务产品 · Layer 03

Business Product / Requirement Funnel / Double-Loop Governance

ENTERPRISE SDD FRAMEWORK
CROSS-ROLE · DOUBLE-LOOP

Balance 权衡 · 轻量 ↔ 易用 ↔ 有效

跨角色大规模协作多 Epic 并行需持续架构演进
轻量 最重

门禁最多、HITL 最多，落地门槛最高；但完整而不臃肿——治理力度随复杂度自适应。

易用 中

各司其职：PM 管业务语义，Engineer 管实现；交接契约化，跨侧不互相等待。

有效 最强

需求/交付解耦 + 分层 Sync = 最高防漂移，可审计、可追溯、可规模化。

何时选它 · 平衡点

效率与治理的胜负手在分层 Sync：Spec Sync 逐 change 回流、Baseline Sync 到 Epic 收尾才做——避免中间态污染。

警示 · 别踩

面向复杂业务，治理力度随复杂度自适应，不陷入文档膨胀与过度治理（完整版 §3.7「Complexity-Balanced」）。

真实案例锚点

epic-accounts-receivable（3 Story → 9 change → Baseline）epic-miniprogram-channel（登录/下单/配置）

Baseline 资产 · 何时合并（重要）

domain_model.html

业务边界 / BC→Capability 映射 / 聚合与不变量

business_process.html

L1/L2/L3 流程节点（验收引用源）

service_blueprint.html

跨角色泳道 / 旅程阶段 SB-STAGE-* / SB--*

ROADMAP.md / PRODUCT.md

规划基线：阶段即 Epic / 定位与决策准则

Spec Sync（change 级）每个 change 归档前回流主规格，保证下一 Story 依赖最新 specs；Baseline Sync（Epic 级）在 Epic 全部 Story 归档后统一回流三件套 + Roadmap——避免单个 Story 中间态污染 baseline、避免反复改写；到点须显式判定（Needs Sync 或 No-op 均记录）。
