Business Process Baseline

以分层流程建模方式沉淀业务基线：L1 聚焦端到端价值流，L2 展开关键价值段，L3 下钻单个关键业务环节。 本页用于统一业务视角、领域边界和后续 Spec/Capability 设计的语义起点。

Purpose

把流程分层，避免把价值流、协同流和规则流画在同一张图里

这份基线把流程建模拆成三个层级：L1 只回答“客户价值如何端到端完成”，L2 只回答“某个价值段如何跨角色/能力域协同推进”， L3 只回答“某个关键环节的业务规则与状态如何精细执行”。这样既能保证高层可读，也能为 Capability 与设计规格提供稳定输入。

Modeling Lens

L1
端到端价值流，突出业务里程碑和价值交付，不展开系统细节。
L2
某个价值段的协同流程，突出角色、能力域交接、关键状态与业务判定。
L3
某一业务环节的规则执行流，突出准入、校验、状态变化、补偿与异常回退。

分层建模规范

作为业务流程基线，L1 和 L2 需要先被规范化，再允许某些关键节点进入 L3 细化。下面的定义可以直接作为后续流程产物的统一口径。
L1 Process
Value Stream

整体端到端价值流

以客户价值交付为主线，覆盖“从需求触发到订单完成”的主要阶段，只保留关键业务里程碑、输入输出和责任归属。

  • 推荐粒度：5 到 8 个阶段。
  • 表达重点：阶段目标、进入/退出条件、主责能力域。
  • 不进入接口、算法、数据表或系统补偿细节。
L2 Process
Value Segment

某个价值段的协同展开

对某个 L1 阶段进行展开，展示参与角色、关键能力域、业务判定点和状态交接。L2 是业务流程 owner 最常用的治理层。

  • 推荐粒度：一个 L1 阶段展开为 5 到 9 个协同步骤。
  • 表达重点：泳道、业务决策、状态变化、跨 BC 交接。
  • 允许出现 Capability/BC，但仍然以业务语义命名。
L3 Process
Business Activity

单个关键业务环节的规则流

对 L2 中某一步做精细展开，例如优惠券核销、库存占用、支付确认等。这个层级用于沉淀规则、异常与补偿，不再追求大图全貌。

  • 推荐粒度：4 到 7 个步骤即可说清规则闭环。
  • 表达重点：触发条件、输入快照、校验规则、成功/失败分支。
  • 通常可直接转译为 Capability 约束和验收标准。

L1 端到端价值流

该层级只保留客户价值主线。这里把电商核心流程规范为 6 个阶段，覆盖从商品发现到履约完成的全链路。
L1 建模原则：每个阶段必须能回答“这一段业务想交付什么价值”“何时算进入/退出该阶段”“由哪个能力域主责”。

L2 价值段展开：下单结算

下单结算是 L1 中最容易跨边界协同的价值段，天然涉及 Cart、Coupon、Order 与 Payment。这里用 L2 展开其业务协同过程，而不是把所有系统细节混入 L1。

进入条件

买家已形成待购买清单，规格已选定，商品当前可售，并具备结算所需的基础上下文，例如身份、地址与购物车快照。

退出条件

成功路径是生成待支付订单并发起支付；失败路径则停留在结算页，明确返回库存、优惠、金额或支付原因，不产生不一致订单。

治理边界

结算编排归属于跨 BC 协同流程，但定价快照、优惠资格、订单创建和支付确认分别由对应能力域承担清晰责任。

L2 建模原则：以“协同”和“状态交接”为主，不把数据库动作、SDK 调用或低层技术补偿直接画成流程步骤。

L3 环节展开：优惠券核销

优惠券核销不应只画成一个“应用优惠券”的动作。对业务而言，它至少包含资格判断、最优方案试算、订单绑定、支付后正式核销以及失败释放等完整规则闭环。

L3 的业务边界

L3 只展开“优惠券核销”这一环节，不再重复整段结算流程。它关注的是规则与状态，而不是页面导航。

  • 输入对象：购物车/结算快照、候选券集合、用户身份。
  • 输出对象：已选优惠方案、订单绑定关系、券状态变化。
  • 典型状态：可用、已占用、已核销、已释放。

建模建议

如果某个环节存在明确规则判断、跨状态迁移或失败补偿，它就适合进入 L3。优惠券正是典型例子。

  • 预览优惠与正式核销应分开建模。
  • 占用时点与释放时点必须清晰，不可隐含。
  • 最优券选择属于业务规则，不是前端展示逻辑。

与 Capability 的关系

L3 最适合作为 Capability 细化的输入，例如“最优配券”“优惠资格校验”“支付失败释放优惠资源”等。

  • 可直接产出验收条件与异常场景。
  • 可映射到 Coupon BC 与 Order BC 的协作契约。
  • 避免在设计阶段重新解释业务语义。
环节 关键业务规则 成功产物 失败/补偿
资格校验 校验用户归属、适用商品范围、门槛金额、有效期、叠加规则。 形成可参与试算的候选券集合。 不满足条件时给出明确不可用原因，不占用券。
最优试算 基于订单快照与财务精度规则，计算最优优惠组合与应付金额。 返回优惠明细、优惠额和实付金额。 若券失效或上下文变更，需要重新试算并刷新结果。
订单绑定 提交订单时，将选定券与订单快照绑定，防止金额与券不一致。 生成带优惠快照的待支付订单。 订单提交失败则不进入正式占用，回到结算态。
正式核销 支付成功后才把券从“占用”推进到“已核销”。 形成不可重复使用的核销记录。 支付超时、取消或失败时释放占用的券。
结论上，L1 是“看价值”，L2 是“看协同”，L3 是“看规则”。当前页面已按这个口径完成规范化，可继续沿同一模式补充“库存占用”“订单取消”“售后申请”等其他 L3 环节。
