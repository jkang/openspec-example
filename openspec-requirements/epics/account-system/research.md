## Epic 背景 (Epic Context)

- **Epic 一句话**：让订单、优惠券、回款拥有真实的归属主体 —— 用户账户体系（注册/登录/会话），替换 `user_dev` 占位用户，为「回款与应收账款闭环」奠定基础。
- **所属阶段**：下一阶段（Phase 4）「用户资产与账户体系」。当前 Baseline 已闭环「订单生命周期与履约」（Phase 3），系统核心交易与运营闭环已成形。
- **调研触发**：系统当前所有订单、优惠券实例的归属主体均为占位用户 `user_dev`（见 SB-BACKSTAGE-04 的 `GET /api/orders?userId=` 归属隔离接口），B 端无法区分真实买家，「我的订单」无法按真实用户查询。

## 访谈原始记录 (Interview Raw Notes)

> ⚠️ 组成部分（内嵌，非独立文件）：调研过程中的一手原始记录，是后续所有分析的证据来源。

### 访谈记录 1：林晓明（C 端买家）
- 时间/方式：2026-08-27 线上语音访谈（约 20 分钟）
- 原始摘录：
  - "我上次买的那件纯棉圆领 T 恤，想看看发没发货，结果只能凭订单号去问客服，页面里翻不到我自己的订单。"
  - "购物车里的东西，换个浏览器就没了，我觉得应该是跟着我账号走的。"
  - "如果每次都要填一堆资料才能买，我可能就不买了，最好手机号加密码就行。"
- 关键信号：
  - **订单归属缺失**：买家无法查看"我自己的订单"，「我的订单」查询需要登录后按真实用户归属。
  - **购物车跨端**：购物车期望按用户归属（当前仅 sessionId，跨浏览器丢失）。
  - **注册门槛敏感**：注册流程需极简（手机号+密码），拒绝复杂表单。

### 访谈记录 2：陈运营（B 端运营）
- 时间/方式：2026-08-27 线上访谈（约 25 分钟）
- 原始摘录：
  - "订单列表里全是 user_dev，我想知道这个单是哪位顾客的，只能靠猜，或者让客服去对聊天记录。"
  - "之前给老客户单独发券，系统提示一个用户一个模板只能发一次，可我根本不知道哪些号是同一个人的。"
  - "我想在后台能看到用户列表，比如按手机号搜一下这个顾客买了什么，而不是在订单里大海捞针。"
- 关键信号：
  - **B 端需要用户视角**：订单/发券需要真实用户归属，后台需要用户管理入口（用户列表、按手机号/昵称检索、查看用户订单）。
  - **一人多订单聚合**：运营需按"同一用户"聚合订单行为，为后续回款/客诉提供依据。
  - **权限提示**：用户管理属于敏感操作，应限定运营/管理员角色可见（提及"不该让每个客服都能看全量用户资料"）。

### 访谈记录 3：周工（技术负责人）
- 时间/方式：2026-08-28 代码走查 + 访谈（约 40 分钟）
- 原始摘录：
  - "现在订单接口里 userId 全是写死的 user_dev，购物车只认 sessionId，没有真正的认证层。"
  - "认证要零依赖、极简，不要引第三方 OAuth，用文件或内存会话就能跑，跟现在的 JSON 文件持久化风格一致。"
  - "前端 Vue 那套登录态要能刷新不掉——就是会话要持久化，不然体验很割裂。"
  - "做了账户体系之后，订单查询、优惠券发放的归属逻辑都要改成读真实 userId，改动面不小，建议按 Epic 拆 Story。"
- 关键信号：
  - **技术约束**：零第三方认证依赖；会话用内存/文件持久化（对齐现有 JSON 存储风格）；无第三方 OAuth。
  - **会话保持**：刷新不掉登录态（会话持久化）。
  - **改动面**：订单（order-management）与优惠券归属逻辑需修改；需按 Epic 拆分。

## 原始需求信息 (Raw Requirements)

**C 端（买家）想要什么：**
- 注册/登录（手机号 + 密码即可，流程极简）。
- 登录后能看到"我的订单"（按真实用户归属查询）。
- 购物车与登录态跨浏览器/刷新保持。

**B 端（运营）想要什么：**
- 订单列表中能看到真实买家身份（替代 `user_dev`）。
- 后台用户管理入口：用户列表、按手机号/昵称检索、查看单用户订单。
- 用户资料访问受权限约束（敏感操作，非全员可见）。

**技术侧诉求：**
- 零第三方依赖的极简认证（文件/内存会话）。
- 用户基础信息仅昵称 + 联系方式（手机号）。
- 现有 `order-management`、`coupon-management` 的归属逻辑需从 `user_dev` 迁移到真实 `userId`。

**现状痛点汇总：**
1. 「我的订单」无法按真实用户查询（Exit Criteria ①② 的直接来源）。
2. 未登录可下单/查订单，无登录引导（Exit Criteria ②）。
3. 会话不持久，刷新即丢（Exit Criteria ③）。
4. B 端运营无法区分买家身份，发券/客诉靠人工对聊天记录。

## 业务约束与规则线索 (Constraints & Rule Clues)

- **技术约束**：零第三方认证依赖；无 OAuth；会话用内存/文件持久化（对齐 JSON 文件持久化风格）；支付仍模拟。
- **Out of Scope（来自 ROADMAP）**：第三方 OAuth、多地址管理、积分/会员等级、支付渠道。
- **权限线索**：用户管理入口应限运营/管理员角色，普通客服不可见全量用户资料（B 端敏感操作）。
- **归属规则线索**：
  - 订单归属：订单创建时绑定当前登录 `userId`（替换 `user_dev`）。
  - 购物车归属：`Cart (userId, sessionId, items)`——登录后购物车跟随用户（domain_model.html 的 Cart Aggregate 已含 `userId` 字段）。
  - 优惠券归属：`Coupon.userId` 已存在，发券需基于真实用户。
- **注册信息**：昵称 + 手机号 + 密码；手机号唯一性需校验（暗示用户表唯一约束）。
- **会话保持**：刷新不掉登录态（持久化会话 token / 文件会话）。

## 调研结论 (Research Conclusion)

- **关键发现摘要**：
  1. 账户体系是订单、优惠券、购物车归属统一的**前置基础设施**，改动面横跨现有 `order-management`、`coupon-management`、`cart-management` 的归属读取逻辑。
  2. C 端诉求极简（手机号+密码注册/登录、我的订单按人查、登录态保持）；B 端诉求为**真实用户归属 + 用户管理入口（含权限约束）**。
  3. 技术约束明确：零第三方认证依赖、文件/内存会话、JSON 持久化风格。
- **Epic key 识别**：本调研对应 ROADMAP「用户资产与账户体系」阶段，识别为 **`account-system`**。
- **是否足够支撑进入 explore**：✅ 是。原始需求、约束线索、待澄清项（Q-1~Q-6）均已收集，可进入 explore 转化为产品设计思路；待澄清项将在 explore 中以默认方案 + 标注"待确认"处理，并在 HITL 呈报。
