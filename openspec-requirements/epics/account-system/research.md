## Epic 背景 (Epic Context)

- **Epic 一句话**：建立用户账户体系（注册 / 登录 / 会话 + B 端用户管理），让订单、优惠券、未来的回款拥有真实归属主体（真实 `userId`），替换硬编码的 `user_dev` 占位用户。
- **所属阶段**：`docs/ROADMAP.md` 下一阶段「用户资产与账户体系」——目标：让订单、优惠券、回款拥有真实的归属主体，为「回款与应收账款闭环」（阶段 D，`epic-accounts-receivable`）奠定数据主体基础。
- **阶段 Exit Criteria（ROADMAP 原文 ①-③）**：① 注册/登录 E2E 通过（登录后可下单，订单归属当前用户）；② 未登录不可下单/查看我的订单（引导登录）；③ 会话保持（刷新不掉登录态）。
- **In Scope 承诺项（ROADMAP Explore 护栏，需 Story 承接）**：④ 未登录拦截引导登录；⑤ B 端用户管理可用（后台查看用户列表、启停账户，禁用用户无法登录）。
- **阶段 In/Out of Scope（ROADMAP 原文）**：In Scope 为账户注册/登录/会话（基础认证，无第三方依赖）、订单与优惠券按真实用户归属、用户基础信息（昵称/联系方式）；Out of Scope 为第三方 OAuth、多地址管理、积分/会员等级、支付渠道（仍模拟）。
- **Explore 护栏（ROADMAP 原文）**：必须同时提供 B 端视角（用户管理入口评估）与 C 端视角（登录/注册交互）原型；严禁第三方 UI 组件库；零依赖极简认证（内存/文件会话）；真实业务数据，拒绝空洞占位符。

## 原始需求信息 (Raw Requirements)

> 提炼自上方「访谈原始记录」（访谈 1/2/3），贴近原意，不做产品转化。

**C 端（贴近原话/原意）**：

- "下了单之后，我想在「我的订单」里看到的是**我的**订单，不是所有人混在一起的。"（现状：所有订单归属 `user_dev`，无法区分）
- "每次下单都要先登录，最好注册一次以后就不用反复输。"（会话保持诉求）
- "注册别太复杂，邮箱 + 密码就能开始，昵称、手机号这些能补就行。"（注册表单轻量化诉求；本阶段注册时即采集昵称与手机号）

**B 端（贴近原话/原意）**：

- "现在系统里所有订单、优惠券都挂在 `user_dev` 一个占位用户下面，**根本分不清这笔订单是谁下的、这张券该发给谁**。"
- "我需要后台有一个用户列表，能看到谁注册了、什么状态，**不活跃或异常的账户能停用**。"
- "账户被停用后，这个人就不能再登录下单了，**要立即生效**。"

**痛点/现状问题（调研记录）**：

1. 所有买家共享同一身份 `user_dev`，"我的订单"无法按人隔离，归属语义缺失。
2. 无法回答"这笔订单属于哪个真实买家"，营销发券与后续回款对账缺数据主体。
3. B 端无用户管理入口，账户生命周期（启停）无法管控。

## 业务约束与规则线索 (Constraints & Rule Clues)

- **注册规则**：邮箱全局唯一（重复注册拦截）；密码 ≥6 位且同时包含字母与数字；采集昵称（≤20 字符）与 11 位手机号。
- **账户状态机**：`ACTIVE`（注册默认）↔ `DISABLED`（B 端手动启停）；`DISABLED` 立即禁止登录。
- **会话**：登录成功下发令牌，30 天有效；刷新不掉登录态；退出登录立即失效。
- **归属语义**：登录后**新订单** `userId` 归属当前登录用户；**存量 `user_dev` 数据不迁移**（保留并视为无归属，不显示在任何真实用户「我的订单」中）；新发券实例 `userId` 非空归属真实用户。
- **权限**：后台单一 Admin 角色（与现有商品/订单管理同权），无细粒度 RBAC。
- **技术限制**：零第三方依赖（无 OAuth / 无短信 / 无邮箱验证码）；认证用内存/文件会话（`sessions.json`，`token → { userId, expiresAt }`）。

## 疑问与待澄清项 (Open Questions)

1. **密码存储方式**：演示期明文 or 哈希？→ 倾向：实现保留 hash 语义，演示环境可明文，待开发侧确认。
2. **会话有效期**：固定 30 天是否满足买家"1 天跑通主流程"习惯？是否需要滑动续期？→ 倾向：固定 30 天，不做 sliding expiration（本阶段）。
3. **手机号必填性**：手机号是否必填？是否与短信验证解耦？→ 倾向：必填但仅 11 位格式校验，本阶段无短信验证码。
4. **存量 `user_dev` 数据可见性**：存量订单/优惠券是否在「我的订单」/运营报表中可见？→ 已倾向决策：不迁移、视为无归属、不显示在真实用户视图（待 HITL 复核）。
5. **禁用账户可否恢复**：`DISABLED` 是否允许重新 `ACTIVE`？→ 倾向：允许，作为生命周期完整闭环（启停双向）。

## 调研结论 (Research Conclusion)

- 需求真实且与 ROADMAP 下一阶段「用户资产与账户体系」**完全对齐**：账户体系是回款闭环（阶段 D `epic-accounts-receivable`）的前置数据主体条件。
- C 端核心诉求 = 真实归属的"我的"体验（注册/登录/会话）；B 端核心诉求 = 用户池可见 + 生命周期可管控（启停）。
- 约束与规则线索已足够支撑进入 explore（转化 To-Be Process / To-Be Journey / 候选 Capabilities）；5 个待澄清项均已给出倾向性结论，待用户 HITL 确认。
