## Epic 背景 (Epic Context)

- **Epic 一句话（业务意图）**：让小程序买家在支付成功后获得积分，能查看余额与明细、用积分兑换权益；B 端能配置积分规则、处理补发/扣减并留痕，把"一次性成交"变成"可识别的复购关系"。
- **所属阶段**：**Phase 9「会员与复购」**（2026-10-20 用户裁定并已登记 `docs/ROADMAP.md`；登记前调研记录为"未登记"，见下方缺口说明）。
- **ROADMAP 缺口（调研时如实记录；已于 2026-10-20 由规划层登记闭环）**：
  - 调研时 `docs/ROADMAP.md` 的「当前 Baseline」只列出 Phase 6（微信小程序渠道）与 Phase 7（应收账款）完成。
  - 调研时「未来 +1 个月」为 **Phase 8 运营效率增强**（订单批量处理/数据导出/常用查询保存），**不含会员积分**。
  - 调研时「未来 +X 个月 — 探索方向（未排期）」只提到多仓/多店铺、供应商协同、复杂促销引擎（满减/阶梯价）、真实微信支付与订阅消息推送，**同样不含积分/会员**。
  - 历史证据：`openspec-requirements/archive/2026-08-29-account-system/research.md` 与 `idea.md` 明确把「积分/会员等级」列为 Phase 4 的 **Out of Scope**，说明这是历史延后能力，而非当时的阶段承诺。
  - 处理方式：本文件只记录缺口（调研阶段不自行修改规划）；Epic 如何登记 ROADMAP 属规划层（`/opsx:planning:product-planning`）职责，需 HITL 裁定（见「疑问与待澄清项」Q1）。
  - **闭环结论（2026-10-20）**：Q1=A——新增 **Phase 9「会员与复购」**，首个 Epic 即 `epic-miniprogram-membership-points`，已写入 `docs/ROADMAP.md`（含 In/Out of Scope、Exit Criteria、Explore Guardrails 与 draft Story 拆分）。**本 Epic 已具备 handoff 的规划依据**，Phase 8 延后评估。
- **可复用的前置底座（现状事实）**：
  - 订单生命周期 `PENDING_PAYMENT → PAID → SHIPPED → COMPLETED / CANCELLED`，支付成功时扣库存、核销券、写 `paidAt`。
  - 同源账户体系（手机号注册/登录 + 微信 openid 登录），角色 `客户 / 运营 / 客服 / 老板`，会话带来源渠道 `channel`。
  - 优惠券闭环（规则创建 → 单人发放 → 结算最优券 → 支付时核销，发放记录含操作人）。
  - 小程序原生工程（首页/详情/购物车/结算/我的订单），Web 与小程序同库同源。
  - 应收账款：账期客户 `creditDays > 0`，下单时服务端信用放行直接置 `PAID`，发货后生成应收。
  - JSON 文件持久化（`data/*.json`，FileStore 全量原子落盘）。
- **调研触发**：用户提出「小程序会员积分」Epic，要求先做需求调研；调研中同时发现规划缺口与现状约束，需在 explore 前由用户裁定。

## 访谈原始记录 (Interview Raw Notes)

> 组成部分（内嵌，非独立文件）：以下是场景化模拟的一手记录，作为后续 explore 的证据来源；关键信号统一编号，便于追溯。

### 访谈记录 1：林采购（目标买家 / 下游企业采购员）

- 时间/方式：2026-10-20 线上访谈（约 25 分钟），围绕"小程序下单后的留存与激励"。
- 原始摘录：
  - "我上周在小程序买那台极简机械键盘，299 元，9 折券减了 29.90，实付 269.10 —— 要是按 299 给我积分，我肯定觉得你们算错了。"
  - "我们这种小公司采购，鼠标 89、支架 68、显示器 1299 都买过，一年下来不是小数；可你们现在只认订单，不认我买了多少次、买了多少。"
  - "小程序点『我的』进去就是订单列表，没有余额、没有明细，我根本不知道有没有积分、攒了多少。"
  - "别让我为了兑 10 块钱去算半天；最好结算时直接告诉我这单能抵多少，剩下的积分还剩多少。"
  - "老客户和一次性客户要是待遇一样，我为什么非在你们这买？"
- 关键信号：
  - S1-① **计发基数要可解释**：买家天然按"实际付的钱"理解积分，券让利部分是否计发会直接影响信任。
  - S1-② **复购识别缺失**：当前只有订单归属，没有累计消费/购买频次的可感知回馈。
  - S1-③ **C 端触点缺位**：小程序「我的」= 订单页，无余额/明细/兑换入口；买家不知道积分存在。
  - S1-④ **兑换要极简**：结算页直接显示可抵金额与剩余积分，避免二次计算。
  - S1-⑤ **差异化待遇**：老客户/高频客户希望被识别，与一次性客户有区别。

### 访谈记录 2：李老板（贸易型中小企业老板）

- 时间/方式：2026-10-20 线上访谈（约 25 分钟），围绕"让利投入与复购回报"。
- 原始摘录：
  - "优惠券我一年发出去多少、让利多少，销售看板能看到 discountCents；但客户拿了好处还来不来，我看不到。"
  - "积分不是不能给，是要有一本账：发了多少、兑了多少、过期多少、还剩多少，月底能对上。"
  - "林明贸易那种 45 天账期的客户，货发了钱还没回，积分先给出去；这单要是黄了，积分怎么收回来？"
  - "等级折扣先别急着上。等级要配权益，客服解释不清，客户一吵就是我们的错。先把积分跑通。"
  - "规则谁配谁负责，我只看看板；运营配错了，得能查到是谁改的。"
- 关键信号：
  - S2-① **积分被当作复购度量**：现有看板只有销售额/让利，缺少"客户是否回来"的可见指标。
  - S2-② **必须有一本总账**：发放/兑换/过期/结余可对账，不能是一笔糊涂账。
  - S2-③ **账期客户存在资金与积分错配风险**：信用放行即 `PAID`，现金未回，积分先兑付可能形成损失。
  - S2-④ **等级是独立增量**：老板倾向本期先跑通积分，等级权益（折扣/包邮/优先发货）后置，避免客服解释成本与范围膨胀。
  - S2-⑤ **权限与审计**：老板只读；运营可配但必须留操作人与变更记录。

### 访谈记录 3：陈运营（B 端运营）

- 时间/方式：2026-10-20 线上访谈（约 30 分钟），围绕"配置、发放、风控与客服处理"。
- 原始摘录：
  - "优惠券这边已经有 FLAT、PERCENTAGE、门槛、有效期、单人发放、发放记录；积分再换一套券，我两边对不上。"
  - "补发和扣减一定留痕：谁、什么时候、多少分、为什么。发券记录里有 operator，积分不能没有。"
  - "客服每天被问『我积分怎么少了』，他至少要能查明细，但绝对不能改。"
  - "同一个客户网页下过单、小程序也下过单，积分不能两个池子；但活动要是只补小程序，规则得能分渠道。"
  - "现在订单、商品、优惠券这些老后台接口其实没做服务端角色校验，全靠前端藏菜单；积分要是也这么做，迟早出事。"
- 关键信号：
  - S3-① **积分换券必须与 coupon-management 同源**：现有券有规则模板/实例/发放记录，不能另起一套券池造成对账分裂。
  - S3-② **手工调整必须有审计字段**：操作人、时间、分值、原因、关联单据缺一不可。
  - S3-③ **权限分层诉求明确**：运营可配/可调、老板只读、客服只查不可改。
  - S3-④ **账户与渠道要分开看**：积分账户按 User 唯一（Web/小程序同源）；"是否只对小程序订单计发"是规则维度，不是账户维度。
  - S3-⑤ **服务端门禁是现实缺口**：既有部分 B 端端点无角色校验，新增写操作若沿用旧模式会有越权风险。

### 访谈记录 4：周工（技术负责人 / 代码与规格现状走查）

- 时间/方式：2026-10-20 代码走查（约 40 分钟），逐项核对 `openspec/specs/`、`ecommerce/ecommerce-mini/`、`ecommerce/ecommerce-miniprogram/`、`ecommerce/ecommerce-mini-frontend/`。
- 原始摘录：
  - "全仓 grep `points/积分/会员/loyalty` 没有业务命中，现有 18 个 capability 里也没有积分；这是全新领域，不是给 User 加个字段就完事。"
  - "能复用的是事实和底座：`PaymentService.pay()` 在支付成功一个点里扣库存、核销券、写 `paidAt`；`User` 有 `id/role/status/openid/creditDays`；`Session` 有 `channel`；`FileStore` 是 JSON 全量原子落盘。"
  - "改动面至少是：新领域对象 + 新持久化文件、C 端余额/明细/兑换接口、小程序新页面（现在 tabBar 只有首页/购物车/我的=订单，没有个人中心）、B 端规则配置与流水页、E2E。"
  - "几个硬约束：金额全是 cents 整型；没有运费字段；没有退款；取消只允许 `PENDING_PAYMENT`；账期客户下单时服务端直接信用放行置 `PAID`，钱其实还没到。"
  - "订单定义了 `COMPLETED`，但没有 HTTP 路由，`markCompleted` 只在单测里用；线上实际能到的是待支付/已支付/已发货/已取消。"
  - "小程序是原生工程，仓库 E2E 是 Playwright 跑 Vue + Node；后端契约能测，小程序页面本身没有自动化。"
  - "B 端权限不统一：用户管理/看板/库存/应收/渠道有 `requireRole`，订单/商品/优惠券管理端点没有服务端角色门禁。"
- 关键信号：
  - S4-① **零基础新领域**：现有规格与代码均无 points 概念，不存在可改造的积分字段或流水。
  - S4-② **可复用底座明确**：支付成功单点、User 账户、Session 渠道、角色白名单、JSON 持久化、E2E 契约测试。
  - S4-③ **改动面跨端**：领域对象/持久化 + C 端 API + 小程序页面 + B 端配置/流水 + E2E。
  - S4-④ **售后语义缺失**：无退款、取消仅限待支付、账期客户"PAID 但未收款"、无运费；积分回滚口径必须建立在这些事实之上。
  - S4-⑤ **订单终态不完整**：`COMPLETED` 无入口，积分若绑定"完成"会长期不触发。
  - S4-⑥ **小程序验证降级**：原生页面无自动化，只能以后端契约 E2E 兜底。
  - S4-⑦ **服务端权限不统一**：部分 B 端端点有 `requireRole`，订单/商品/优惠券管理端点没有；新增积分写操作不能照搬旧模式。

## 原始需求信息 (Raw Requirements)

- **买家想要什么**：
  - 支付后能感知到积分（余额、明细、来源订单），不用猜。
  - 计发口径符合"我实际付了多少"的直觉（券让利部分不应被重复奖励）。
  - 结算时能用积分直接抵现，且能看到抵扣上限与剩余积分；兑换路径要短。
  - 作为老客户/高频采购，希望被识别（等级或累计权益），而不是与一次性客户同等待遇。
- **老板想要什么**：
  - 一个能衡量复购的抓手，补足现有销售看板"只看卖了多少、看不到客户回不回来"的空白。
  - 一本可对账的积分总账（发放/兑换/过期/结余），以及规则变更与人工调整的审计。
  - 对账期客户（如 `creditDays=45`）的积分兑付风险有控制手段。
  - 本期范围收敛：先积分，等级权益后置；老板只读，运营可配可控。
- **运营想要什么**：
  - 积分规则可配置（获取比例、有效期、兑换比例/上限），配置后即时生效。
  - 积分换券复用现有券体系与发放记录，避免两套券池。
  - 补发/扣减可操作、必留痕（人/时间/分值/原因/关联单）。
  - 客服可查明细、不可改；运营可写；老板只读；服务端要有真实门禁。
  - Web 与小程序同一积分账户，不因渠道分裂；但规则可按渠道区分。
- **现状痛点**：
  - 系统完全没有积分/会员概念，买家下单后没有任何留存反馈。
  - 小程序「我的」只有订单列表，没有余额/明细/兑换入口；Web 也无个人中心。
  - 优惠券只能"发券让利"，无法表达"消费越多、回馈越多"。
  - 无退款、无运费、订单终态不完整，导致"积分怎么回滚/什么时候算完成"缺少现成语义。
  - 部分 B 端写接口无服务端角色门禁，新增积分写操作存在越权隐患。

## 业务约束与规则线索 (Constraints & Rule Clues)

> 以下均为**线索**，不是定稿规则；最终口径在 explore 阶段与用户确认。

### 1. 积分定位线索

- 三种诉求同时存在，且并不等价：
  - **拉复购**（老板）：用积分把一次性客户变成可识别的回头客，关注兑付成本与复购率。
  - **让利替代**（运营/老板）：现有优惠券是"直接减钱"，积分是"延迟兑现"，可降低即时让利率但增加负债感。
  - **会员分层**（买家/老板）：用累计消费或积分区分待遇，但等级权益会引入折扣、包邮、优先发货等新规则。
- 老板明确倾向"本期先积分、等级后置"（S2-④）；买家则更关心"老客户有没有区别"（S1-⑤）。两者存在张力，需 explore 定范围。
- 线索：积分可能同时承担"复购度量"与"让利工具"两种角色，但不应在未确认前假设二者都做。

### 2. 获取口径线索

- 现有订单同时具备 `totalCents`（商品总额，券前）、`discountCents`（券让利）、`actualPaidCents`（实付）。样例：`29900 / 2990 / 26910`。
- 买家直觉是按 `actualPaidCents` 计发（S1-①）；若按 `totalCents` 计发，等于对券让利部分再次奖励，成本与解释都更复杂。
- 现系统**无运费字段**，"是否排除运费"在本项目暂不构成实际分支；但需记录为口径前提，避免未来加运费时返工。
- 计发形式未定：固定分值（如 1 元 = 1 分）、按比例（如实付金额 × 比例）、按下单次数固定值。
- 是否按商品/分类设置倍率（如高清显示器 1299 元高客单、桌面收纳架 45 元低客单）未定；现商品有 `categoryId`，具备分类维度基础。
- 金额为 cents 整型，按比例计发必然产生小数，需要明确取整规则（向下取整/四舍五入）与最小计发单位。

### 3. 回滚线索

- 取消：仅 `PENDING_PAYMENT` 可取消，取消时未扣库存、未核销券。若积分在支付成功时计发，则"取消"天然不涉及积分回滚；若提前计发则必须回滚。
- 退款：**现系统无退款接口、无退款状态**。一旦积分已发放，缺少"退款 → 扣回积分"的现成链路；若本期引入退款，属额外范围。
- 账期客户：`creditDays > 0` 的客户下单时服务端信用放行直接置 `PAID`（`paymentService.pay()` 被调用），但现金要等回款。积分若绑定 `PAID`，会在收款前兑付（S2-③）；若绑定 `SHIPPED` 或"回款登记"，则与现有 `accounts-receivable` 的 Receipt 流水产生依赖。
- 订单终态：`COMPLETED` 无 HTTP 路由（S4-⑤），若积分绑定"完成"将长期不触发。
- 线索：至少存在三种候选触发点——订单 `PAID` / 订单 `SHIPPED` / 应收 `Receipt` 登记；三者对账期客户的风险与实现依赖完全不同，未定。

### 4. 消耗 / 兑换线索

- **积分抵现**：结算页按比例抵扣，需明确抵扣上限（如不超过实付的 X%）、最小支付金额（如至少留 1 分）、以及积分与券的叠加顺序。
- **积分换券**：与现有 `coupon-management` 的关系是核心线索。现有券有规则模板（`FLAT`/`PERCENTAGE`、`minSpendCents`、`expiryDate`）与用户实例（`UNUSED`/`USED`/`EXPIRED`/`ACTIVE`），发放记录含 `operator`；但没有"积分价"字段。若积分换券另建券池，会与现有最优券推荐、核销、发放记录分裂（S3-①）。
- **积分换实物**：现有商品有 `stock` 与软删除语义，但没有"赠品/兑换品"概念，也没有兑换单与库存占用规则；本期是否纳入未定。
- **叠加顺序**：当前结算逻辑是"先按 `subtotalCents` 选最优券并算 `discountCents`，再 `actualPaidCents = max(0, subtotal - discount)`"。券门槛校验用的是券前 `subtotalCents`。积分抵现插入哪一步、券门槛是否受积分影响、积分能否与券同时使用，均未定。
- 线索：兑换方式的优先级与叠加上限，直接决定结算引擎改动面与财务口径，必须在 explore 明确。

### 5. 生命周期线索

- 有效期候选：永久有效 / 每年清零 / N 个月滚动过期。三者对"负债感"和运营解释成本不同。
- 过期提醒：现系统无订阅消息能力，微信侧仅有 mock 网关（`wechatGateway`），真实订阅消息属 ROADMAP 的 +X 探索方向；本期提醒只能考虑站内展示或不做。
- 冻结/黑名单：现有 `User.status` 只有「正常 / 禁用」，禁用会拦截登录与会话；积分账户是否随用户禁用而冻结、解禁后是否恢复，未定。
- 线索：有效期与过期处理需要"过期流水"而非直接改余额，否则无法对账（S2-②）。

### 6. 会员等级线索

- 是否与积分同期做等级，是范围决策而非细节：等级会引入升级/保级规则、权益配置、等级折扣与结算引擎联动。
- 候选权益：折扣（直接影响订单金额与券叠加）、包邮（现系统无运费，**该权益当前无业务落点**）、优先发货（现订单无优先级/履约排序字段）。
- 老板倾向本期不做等级（S2-④）；买家有差异化待遇诉求（S1-⑤）。若不做等级，需明确"累计消费/复购识别"是否以其他轻量形式呈现。
- 线索：等级若做，必须新增权益模型与结算规则；若不做，应显式写入本期 Out of Scope，避免 handoff 后范围漂移。

### 7. C 端触点线索

- 小程序：tabBar 第三项文案是「我的」，但页面实际是 `pages/orders/orders`（订单列表）。要承载积分余额/明细/兑换，需新增页面或重构「我的」为个人中心（含订单入口）。这是真实的结构缺口，不是加一个按钮。
- Web：C 端顶部只有「我的订单 / 购物车」，无个人中心；若要求 Web 同步可见，需要新增入口与页面。
- 账户同源：Web 与小程序共用 `User` 与会话（`user_1004` 同时有 openid 与小程序会话），积分账户天然应按 `userId` 唯一；但"是否只在 C 端小程序展示"与"是否只在此时段计发"是两个不同问题。
- 线索：C 端触点范围（仅小程序 / 小程序+Web）会显著影响页面与 E2E 工作量，需确认。

### 8. B 端承诺线索

- 规则配置：获取比例/固定值、有效期、兑换比例与上限、是否按渠道/分类区分；现无对应配置页与配置文件。
- 手工调整：补发/扣减是运营现实需求（S3-②），必须记录操作人、时间、分值、原因、关联订单/用户；现只有优惠券发放记录（`issuance.operator`）可参考。
- 流水查询：发放/兑换/过期/调整记录，需支持按用户、时间、类型查询；客服只查（S3-③）。
- 权限：现系统角色白名单模式为 `requireRole('运营')` / `requireRole('运营','老板')`；但订单/商品/优惠券管理端点无服务端门禁（S4-⑦/ S3-⑤）。积分的写操作（配置、补发、扣减、兑换核销）若沿用旧模式会有越权风险。
- 线索：B 端承诺至少包含"可配置、可调整、可查询、可审计、可门禁"五项，具体页面归属未定。

### 9. 渠道与账户线索

- `Order.channel` 为创建时写入的不可变属性（`WEB` / `MINIPROGRAM`），由会话来源继承、服务端判定、防客户端伪造；存量订单缺省视为 `WEB`。
- 现只有 1 笔真实订单且为 `MINIPROGRAM`（`order_cy0jdzhd8`），Web 订单样本为 0；渠道维度做统计/规则时样本不足。
- 账户线索：同一 `User` 不应有两个积分账户（S3-④）；但"只有小程序订单计发"是规则口径，可能被用作渠道拉新手段。
- 线索：渠道是否影响计发、是否影响兑换入口、是否影响活动范围，三者需分开确认。

### 10. 数据与治理线索（非决策）

- 流水类型线索：`earning`（获取）/ `redeem`（兑换/抵现）/ `expire`（过期）/ `adjust`（人工调整）；每笔需可追溯到 `orderId`、`couponId`、操作人、原因。
- 余额口径线索：余额可由流水汇总推导（账实一致、便于审计），也可单独存余额字段（读取快、需防漂移）；未定。
- 治理归属线索（**仅为线索，不定稿**）：候选 A 为 `User Context` 扩展（积分属于用户资产）；候选 B 为新增 `Loyalty Context`（积分/等级独立边界）；候选 C 为 `Order Context` 扩展（积分随交易事实）。三者对 `domain_model.html` 的 BC→Capability 映射影响不同。
- Capability 线索（**仅为线索，不定稿**）：可能需要新增积分账户/积分规则/积分流水/积分兑换等 taxonomy，名称与拆分待 explore 决定；若新增必须在 `domain_model.html` 标记"新增 taxonomy"。
- 现有 `domain_model.html` 无积分相关 Aggregate/Event/Policy；Baseline Sync 时必然涉及 Domain Model 变更（Epic 级）。

### Q2. 本期积分定位是什么？范围到哪里？

- **为什么必须澄清**：定位决定计发基数、兑付成本、页面与 B 端配置范围；"拉复购 / 让利替代 / 会员分层"三者不可默认同时成立。
- **可选方向**：
  - A) 纯复购激励：支付后计发 + 余额/明细 + 抵现；
  - B) 让利工具：积分替代部分优惠券预算，强调兑付成本可控；
  - C) 会员体系第一步：积分 + 累计消费识别，等级后置；
  - D) 积分 + 等级同期做（范围最大，风险最高）。
- **已裁定（2026-10-20，HITL）**：**A) 纯复购激励**——支付成功后计发 + 余额/明细 + 结算抵现；本期不含会员等级、积分换券、积分换实物，不做"让利替代"的预算替代叙事。

### Q3. 积分按什么基数、什么比例计发？

- **为什么必须澄清**：直接决定成本与买家信任；样例订单 `actualPaidCents=26910` 与 `totalCents=29900` 会算出不同结果。
- **可选方向**：
  - A) 按 `actualPaidCents` 固定比例（如 1 元 = 1 分）；
  - B) 按 `actualPaidCents` 但可配置比例/固定值；
  - C) 按 `totalCents` 计发（对券让利部分也奖励）；
  - D) 引入商品/分类倍率（如高客单显示器倍率更高）；
  - E) 只对 `MINIPROGRAM` 订单计发。
- **附**：取整规则（向下/四舍五入）、最小计发单位、是否排除未来运费，需一并明确。

### Q4. 积分在订单生命周期的哪个时点计发？账期客户怎么处理？

- **为什么必须澄清**：现系统无退款、取消仅限待支付、账期客户下单即 `PAID` 但未收款；触发点选错会造成"钱没收到、积分已兑付"或"订单完成不了、积分不发"。
- **可选方向**：
  - A) 订单 `PAID` 时计发（实现最简单，账期客户风险最高）；
  - B) 订单 `SHIPPED` 时计发（与履约对齐，账期客户仍未回款）；
  - C) 现结客户 `PAID`、账期客户 `Receipt` 登记后计发（最稳，但依赖应收流水与两套口径）；
  - D) 订单 `COMPLETED` 时计发（当前无路由，需先补终态入口）。
- **已裁定（2026-10-20，HITL）**：**C) 现结客户（`creditDays=0`）在订单 `PAID` 时计发；账期客户（`creditDays>0`）在 `Receipt` 回款登记后计发**。部分回款是"按比例计发"还是"结清后全额计发"留待 explore 定稿（Q4-附）。

### Q5. 积分怎么用？本期支持哪些兑换方式？

- **为什么必须澄清**：抵现、换券、换实物的实现面与财务口径差异巨大；换券还牵涉与现有 `coupon-management` 的同源关系。
- **可选方向**：
  - A) 仅结算抵现（改动集中在结算引擎）；
  - B) 仅积分换券（复用券体系，但需增加"积分价"与兑换记录）；
  - C) 抵现 + 换券（覆盖主流，范围中等）；
  - D) 抵现 + 换券 + 换实物（需赠品/兑换单/库存占用，范围最大）。

### Q6. 积分与优惠券的叠加顺序、门槛与上限怎么定？

- **为什么必须澄清**：现结算先用券前 `subtotalCents` 校验券门槛并计算 `discountCents`，再算实付；积分插入位置不同会导致券门槛、实付、积分抵扣三者口径冲突。
- **可选方向**：
  - A) 先券后积分：券按 `subtotalCents` 算，积分抵剩余实付；
  - B) 先积分后券：积分先降低计券基数（可能使券失效）；
  - C) 二者互斥：用券则不可用积分；
  - D) 可叠加但设上限（如积分抵扣不超过券后实付的 30%，且至少留 1 分支付）。
- **附**：是否允许积分抵扣到 0 元、是否影响 `discountCents`/`actualPaidCents` 的财务口径，需明确。

### Q7. 积分有效期与过期处理口径？

- **为什么必须澄清**：有效期决定负债规模与运营解释；过期必须有流水，否则余额无法对账。
- **可选方向**：
  - A) 永久有效（最简单，负债无限累积）；
  - B) 年度清零（如每年 12-31 过期）；
  - C) N 个月滚动过期（按获取批次先进先出）；
  - D) 混合（如基础积分永久、活动积分限期）。
- **附**：是否做站内到期提醒（现无订阅消息能力）、过期前是否冻结兑换，需一并确认。

### Q8. 会员等级是否本期同期做？

- **为什么必须澄清**：等级会引入升级/保级、权益配置、等级折扣与结算联动；老板倾向后置，买家有差异化诉求，属于范围决策。
- **可选方向**：
  - A) 本期只做积分，等级写入 Out of Scope；
  - B) 积分 + 轻量等级（仅展示等级与累计消费，不绑定权益）；
  - C) 积分 + 完整等级权益（折扣/包邮/优先发货）。
- **已裁定（2026-10-20，HITL）**：**A) 本期只做积分，等级写入 Out of Scope**；等级折扣/包邮/优先发货全部后置。
- **附**：若做权益，需注意当前**无运费模型**（包邮无落点）、**无履约优先级字段**（优先发货无落点）。

### Q9. C 端触点范围：只做小程序，还是 Web 同步？

- **为什么必须澄清**：小程序「我的」当前就是订单页，没有个人中心；Web 也只有「我的订单」。触点范围直接决定页面重构与 E2E 工作量。
- **可选方向**：
  - A) 仅小程序：新增个人中心/积分页，Web 不展示；
  - B) 小程序 + Web 同步可见同源余额与明细；
  - C) 仅在小程序结算页展示可抵扣，不建独立积分页（最小改动）。
- **附**：若做小程序个人中心，是否顺带承载订单入口、优惠券、账户信息，需明确边界。

### Q10. B 端权限与手工调整规则？

- **为什么必须澄清**：积分是"可兑付负债"，补发/扣减若无审计会形成资产流失；且现有部分 B 端端点无服务端角色门禁。
- **可选方向**：
  - A) 运营可配置/可补发/可扣减，老板只读，客服只查（推荐分层，但需实现服务端门禁）；
  - B) 仅运营可写，老板与客服均不可见；
  - C) 设置调整上限/审批（如单次扣减超过 1000 分需二次确认）。
- **附**：手工调整是否必须填原因、是否允许调整已过期积分、是否允许对禁用用户操作，需明确。

### Q11. 渠道是否影响积分计发与使用？

- **为什么必须澄清**：`Order.channel` 已存在且不可变，但现只有 1 笔小程序订单；"只补贴小程序"是常见拉新手段，也会造成 Web 老客户不满。
- **可选方向**：
  - A) 全渠道统一计发与使用（账户同源，最简单）；
  - B) 仅 `MINIPROGRAM` 订单计发，使用不限渠道；
  - C) 全渠道计发，但小程序专属活动/兑换；
  - D) 按渠道配置不同比例。
- **附**：存量 Web 订单（当前样本为 0）是否追溯，需一并明确。

### Q12. 存量订单是否追溯计发？上线口径是什么？

- **为什么必须澄清**：若追溯，需要一次性补发历史订单（当前仅 1 笔真实订单，但演示/测试数据可能更多）；若不追溯，需向买家解释"以前的消费不算"。
- **可选方向**：
  - A) 不追溯，从上线后新支付订单起算；
  - B) 追溯全部历史 `PAID/SHIPPED/COMPLETED` 订单；
  - C) 追溯近 N 个月；
  - D) 不追溯但提供运营手工补发作为过渡。
- **附**：是否需要种子积分数据用于演示与 E2E，需明确。

### Q13. 积分数据与治理归属怎么定？

- **为什么必须澄清**：决定 `domain_model.html` 的 BC→Capability 映射、规格落位与 Baseline Sync 范围；需求侧不得擅自定稿。
- **可选方向**：
  - A) `User Context` 扩展（积分是用户资产，复用账户边界）；
  - B) 新增 `Loyalty Context`（积分/等级独立边界，长期更清晰）；
  - C) `Order Context` 扩展（积分随交易事实，便于按订单追溯）；
  - D) 混合：账户/余额归 User，流水/兑换归新增 Loyalty。
- **附**：余额是"流水汇总"还是"独立余额字段"、是否需要积分账户快照，也需在 explore 明确。

## 调研结论 (Research Conclusion)

- **关键发现**：
  1. **规划缺口是首要问题**：调研时 ROADMAP 无会员积分阶段/Epic，历史 account-system 明确将其列为 Out of Scope。**已闭环**：Q1=A，2026-10-20 新增 Phase 9「会员与复购」并登记本 Epic，handoff 前置条件已满足。
  2. **诉求真实但分散**：买家要"按实付计发 + 可见 + 易兑换"；老板要"复购抓手 + 一本总账 + 账期风险控制"；运营要"复用券体系 + 留痕 + 权限分层"。
  3. **计发基数与触发点是两个关键口径**：`actualPaidCents=26910` 与 `totalCents=29900` 差异真实存在；账期客户"PAID 但未收款"使 `PAID` 触发点存在兑付风险。
  4. **C 端触点不是加按钮**：小程序「我的」当前就是订单页，无个人中心；Web 也无个人中心，需要页面结构决策。
  5. **现状约束明确**：无退款、无运费、`COMPLETED` 无路由、部分 B 端端点无服务端门禁、小程序页面无自动化；这些都会改变积分回滚、权益与验证方案。
- **数据可行性**：积分是零基础新领域（无字段、无流水、无规格），但订单/用户/会话/券/应收/JSON 持久化底座完整，具备实现条件；主要成本在跨端页面、结算引擎改造与 B 端审计。
- **是否足够支撑进入 explore**：**是（有条件）**。业务线索、用户诉求、现状约束与 13 个待澄清项已足够支撑 explore 做 To-Be 设计与候选 Capability 识别。
  - **条件**：Q1（ROADMAP 登记方式）必须在进入 storymap/handoff 前由用户裁定；Q2（定位与范围）、Q4（计发触发点）、Q8（等级是否同期）是 explore 阶段必须先定的三个关键决策。
  - 若 Q1 选择"仅探索、暂不 handoff"，explore 仍可进行，但 storymap 之后必须暂停。
  - **裁定后更新（2026-10-20）**：Q1=A（新增 Phase 9「会员与复购」）、Q2=A（纯复购激励：计发 + 余额/明细 + 抵现）、Q4=C（现结 `PAID` / 账期 `Receipt` 登记后）、Q8=A（等级 Out of Scope）。Q1 由规划层登记后，explore 可直接启动；剩余待定项收敛为 Q3/Q5（抵现细则）/Q6/Q7/Q9/Q10/Q11/Q12/Q13 与 Q4-附（部分回款计发口径）。
