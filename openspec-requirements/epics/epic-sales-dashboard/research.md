# Research: 销售报表看板 需求调研

> Epic Key: `epic-sales-dashboard`（来自 `docs/ROADMAP.md` Phase 5 Epic 5.1）
> 阶段: Phase 5 数据洞察与经营决策
> 产出后需用户确认（HITL）

## Epic 背景 (Epic Context)

- **Epic 一句话**：销售报表看板——让老板与运营通过真实数据驱动经营决策（销售额/订单量/客单价/优惠让利，时间 × 商品 × 分类维度）。
- **所属阶段**：Phase 5 数据洞察与经营决策（`docs/ROADMAP.md`）。
- **阶段目标**：销售报表看板（Epic 5.1）+ 库存预警与补货建议（Epic 5.2），兑现"可视即价值"。
- **前置现状**：Phase 3/4 已交付订单生命周期闭环与用户账户体系；`Order` 含 `totalCents/discountCents/actualPaidCents/couponId/items/userId/status` 财务字段，`Product` 含 `stock` 且不变量 `stock≥0`；`domain_model.html` 已预留 `Operator 库存看板` ReadModel。

## 调研范围与对象 (Stakeholders)

- **调研对象**：
  1. **老板/决策者**（目标用户画像 · 核心 B 端角色）：需要快速掌握销售全貌，判断经营趋势，不关心操作细节。
  2. **运营人员**（目标用户画像 · 核心 B 端角色）：需要按商品/分类定位销售表现，评估促销（优惠券）效果，支撑选品与补货决策。
  3. **财务/客服**（边缘角色）：偶尔回查订单金额与优惠明细（只读，无看板主诉求）。
- **沟通方式**：场景化访谈（结构化提问）+ 现有系统数据观察（orders.json / products.json / coupons.json 数据审计）。
- **时间与场景**：Phase 5 规划期（2026-08-30）；场景为日常经营周报/月报与促销复盘。

## 访谈原始记录 (Interview Raw Notes)

### 访谈记录 1：老板（决策者）
- 时间/方式：2026-08-30 场景化访谈（线上）
- 原始摘录："我现在每天要看销售额和订单数，都是让运营手动导 Excel 数出来的，慢而且容易错。我就想打开系统第一眼看到今天卖了多少、比昨天好还是差。"
- 关键信号：需要**首屏指标总览** + **时间对比趋势**；痛点=手动统计效率低、易错。

### 访谈记录 2：运营人员（选品/促销负责人）
- 时间/方式：2026-08-30 场景化访谈（线上）
- 原始摘录："我想知道哪个商品卖得最好、哪个分类不行，这样才好决定上什么新品、清什么库存。另外发券之后到底带来多少单、让了多少利，现在完全看不到效果。"
- 关键信号：需要**商品/分类排行** + **优惠让利（优惠券效果）**；痛点=促销 ROI 不可见。

### 访谈记录 3：运营人员（库存管理）
- 时间/方式：2026-08-30 场景化访谈（线上）
- 原始摘录："商品什么时候该补货全凭感觉，卖得快的东西经常断货，卖不动的又压资金。最好有个数字告诉我这周卖了几个、按这个速度还有几天卖完。"
- 关键信号：需要**销量速度**与**预计售罄天数**（衔接 Epic 5.2 库存洞察）；痛点=补货靠经验、断货/压货并存。

### 访谈记录 4：财务（只读回查）
- 时间/方式：2026-08-30 快速访谈
- 原始摘录："我不需要天天看报表，但月底对账时想确认优惠让利和实收对得上，别把券的让利算进销售额里。"
- 关键信号：**口径约束**——销售额必须以 `actualPaidCents`（实付）为准，优惠让利（`discountCents`）单列，不可混淆。

## 原始需求信息 (Raw Requirements)

- 老板：打开系统首屏即见今日销售额/订单量，且能对比昨日/近7日/近30日趋势。
- 运营：能按商品、分类查看销售排行（TOP10），评估优惠券让利效果。
- 运营：能根据销量速度判断补货时点（售罄天数），避免断货/压货。
- 财务：销售额口径 = 实付金额（actualPaidCents），优惠让利单列，确保对账一致。
- 全角色：看板为**只读聚合**，不改变订单/库存语义；数据必须与订单明细一致。

## 业务约束与规则线索 (Constraints & Rule Clues)

- **口径约束**：销售额 = `SUM(actualPaidCents)`；优惠让利 = `SUM(discountCents)`；订单量 = 非 CANCELLED 订单计数（或需明确是否含取消——待澄清）。客单价 = 销售额 / 订单量。
- **时间维度**：订单按支付时间（paidAt，PAID 状态后）归属统计；未支付（PENDING_PAYMENT）与取消（CANCELLED）不计入销售。
- **权限约束**：看板 API 仅 `role=运营` 或新增 `老板` 角色可访问；`客户 / 客服` 403（对齐 R-ADM 权限门禁模式）。
- **只读约束**：看板为聚合只读，不产生写操作。
- **数据一致性**：E2E 断言看板指标与订单明细一致。
- **极简 UI**：slate 色系、无圆角阴影、零第三方图表库（CSS/SVG 实现趋势与条形）。

## 疑问与待澄清项 (Open Questions)

1. 订单量统计口径：是否计入 CANCELLED？倾向"不计入"（销售=成交），需确认。
2. 「老板」角色：是新增独立角色，还是复用 `role=运营` 的权限？倾向新增 `老板`（只读看板，无管理权限），需确认。
3. 时间切换默认值：首屏默认"今日"还是"近7日"？倾向默认近7日（趋势更有意义），需确认。
4. 是否需要分类聚合下的二级商品明细？倾向"商品排行全局 + 分类排行全局"两级即可，不做联动下钻（保持极简）。
5. 优惠让利维度：只展示总让利，还是按券类型（FLAT/PERCENTAGE）拆解？倾向总让利 + 用券订单数（简单有效）。

## 调研结论 (Research Conclusion)

- **关键发现**：① 看板首屏指标 + 时间趋势是老板硬需求；② 商品/分类排行与优惠让利是运营选品与促销复盘刚需；③ 销量速度→售罄天数衔接 Epic 5.2；④ 财务口径（实付 vs 让利）是硬约束。
- **数据可行性**：`Order` 财务字段完整、`paidAt` 可支撑时间聚合，数据资产就绪，无技术阻断。
- **是否足够支撑进入 explore**：✅ 是。调研信息完整，5 个待澄清项将在 explore 与用户确认后定稿。
