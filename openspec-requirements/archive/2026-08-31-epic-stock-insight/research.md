# Research: 库存预警与补货建议 需求调研

> Epic Key: `epic-stock-insight`（来自 `docs/ROADMAP.md` Phase 5 Epic 5.2）
> 阶段: Phase 5 数据洞察与经营决策
> 产出后需用户确认（HITL）

## Epic 背景 (Epic Context)

- **Epic 一句话**：库存预警与补货建议——低库存预警列表（阈值可配置，含超卖风险标识）+ 基于销量速度的补货建议（预计售罄天数 + 建议补货量）；B 端预警阈值配置（谁配置 / 生命周期 / 权限）。
- **所属阶段**：Phase 5 数据洞察与经营决策（`docs/ROADMAP.md`）。
- **阶段目标**：让**老板与运营**通过真实数据驱动经营决策——销售报表看板（Epic 5.1 已交付）+ 库存预警与补货建议（Epic 5.2），兑现"可视即价值"。
- **前置现状**：
  - Epic 5.1 `epic-sales-dashboard` 已交付并归档：`data-insights` Bounded Context 与 `sales-dashboard` capability 已进入 `docs/baseline/domain_model.html`（bc-data-insights 节点行 ~939 / cap-sales-dashboard 行 ~954 / Governs 边行 ~970）。
  - `Product.stock` 为真实库存事实：Aggregate 不变量 `stock≥0`（domain_model 行 ~891）；支付成功后二次校验并扣减库存（`ecommerce/ecommerce-mini/src/services/payment.js` 行 27-39，`OUT_OF_STOCK` 时订单保持 PENDING_PAYMENT）。
  - `domain_model.html` 行 ~877 已前瞻预留 ReadModel `['Operator', '库存看板', '运营查看销量与补货状态。']`，为 Epic 5.2 的治理锚点。
  - 前端设计系统（`docs/baseline/design-system/`）已有 `--warning`（#FF9A00）语义令牌，定义为 "Limited, low stock"，可直接用于低库存预警标识。

## 调研范围与对象 (Stakeholders)

- **调研对象**：
  1. **运营人员（库存管理）**（目标用户画像 · 核心 B 端角色）：负责日常库存水位与补货，最痛断货/超卖。
  2. **老板（决策者）**（Epic 5.1 已新增角色 · 只读看板视角）：需要全局库存健康度，衔接销售看板判断经营。
  3. **运营人员（商品管理，既有 product-admin 用户）**（目标用户画像 · 核心 B 端角色）：日常在商品管理中维护库存数字，是阈值配置职责的候选承担者。
  4. **数据观察**（系统数据审计）：products.json 库存分布、订单销量速度可计算性、权限门禁与设计令牌现状。
- **沟通方式**：场景化访谈（结构化提问）+ 现有系统数据观察（products.json / orders.json / order.js 聚合能力审计）。
- **时间与场景**：Phase 5 规划期（2026-08-31）；场景为日常库存巡检与补货决策（跑量款断货预警、慢销款资金占用）。

## 访谈原始记录 (Interview Raw Notes)

### 访谈记录 1：运营人员（库存管理）
- 时间/方式：2026-08-31 场景化访谈（线上）
- 原始摘录："现在断货全靠买家来提醒，售罄了才发现，太被动。我想知道库存低于多少就该备货，最好能按商品分开设线——键盘这种跑量款线要设高一点，氛围灯这种卖得慢的线设低一点。另外最怕超卖，库存明明剩 3 件，一下来了 5 单，支付的时候才发现不够，订单卡在那里不动。"
- 关键信号：① 需要**售罄前预警**而非售罄后被动补救；② 阈值需**按商品/品类差异化配置**（跑量款与慢销款不同）；③ **超卖风险**是明确担忧（现有支付二次校验 `OUT_OF_STOCK` 只能兜底失败，运营看不到风险水位）。

### 访谈记录 2：老板（决策者）
- 时间/方式：2026-08-31 场景化访谈（线上）
- 原始摘录："销售看板我现在能看卖了多少，但库存那边还是运营在 Excel 里管，两块是断的。我想一眼看到整体库存健康度——哪几个商品快卖光了、总共压了多少资金在库存上。别让卖得好的断货，也别让卖不动的压死资金。"
- 关键信号：① 需要**全局库存健康度总览**，与已交付销售看板形成闭环；② 关注**库存资金占用**（库存 = 资金沉淀）；③ 老板仅需**只读总览**，不碰配置操作。

### 访谈记录 3：运营人员（商品管理，product-admin 既有用户）
- 时间/方式：2026-08-31 场景化访谈（线上）
- 原始摘录："我平时就在商品管理里维护库存数字，改库存是我天天干的事。但预警阈值这种东西不用天天改，设好一次管很久。别让我每次都要去配，最好有默认值兜底，我只需要在某个商品快售罄的时候去调它的线。"
- 关键信号：① **阈值配置职责**落在既有商品管理运营，不引入新角色；② **配置频率极低**（低频写操作，设一次长期有效）；③ 需要**默认值**兜底，避免空配置负担；④ 可复用既有 product-admin 操作入口习惯。

### 访谈记录 4：运营人员（库存管理 · 补货决策）
- 时间/方式：2026-08-31 场景化访谈（线上）
- 原始摘录："光告诉我'库存低'不够，我还想知道按现在卖的速度几天卖完、该补多少。补多了一把压资金，补少了过几天又断。最好系统给个建议量，我再按实际到货周期调整。"
- 关键信号：**销量速度 → 预计售罄天数 → 建议补货量**是核心决策链；补货量需权衡**资金占用**与**到货周期**（后两者为探索期候选决策因子，MVP 口径待 explore 确认）。

### 数据观察记录（数据可行性审计）
- 时间/方式：2026-08-31 系统数据观察（products.json / orders.json / order.js / server.js / design-system）
- 原始数据与摘录：
  - `products.json`：6 商品当前 `stock` 均为 99（种子态）；运行态支付成功后逐单扣减，`stock` 为真实库存事实（`payment.js` 二次校验 `product.stock < item.quantity → OUT_OF_STOCK` 后扣减）。
  - `orders.json`：当前落盘为空 `[]`；运行态成交订单具备 `items[{productId, quantity, name, priceCents}]`（订单快照）、`status ∈ SALES_STATUSES = ['PAID','SHIPPED','COMPLETED']`（`order.js` 行 4）、`paidAt`（支付时间，`payment.js` 行 48 PAID 时写入）。
  - 销量聚合：`order.js buildProductRanking`（行 204-226）已实现按 `items.quantity` 聚合的**商品销量（Σ quantity）**，按订单快照不依赖商品表；与 `paidAt` 时间维度结合即可得日均销量。
  - 时间换算：`server.js resolveDashboardRange(dimension)`（行 172 起）已具备 今日/近7日/近30日 换算，可直接复用。
  - 权限门禁：`requireRole('运营', '老板')` 白名单模式已在销售看板落地（`server.js` 行 497/522，R-DASH-006）；种子用户仅 `运营`（user_1001）/`客户`（user_1002），`老板` 无种子演示账号（测试后门可设角色）。
  - 设计令牌：`design-system/src/index.css` 行 22 `--warning: #FF9A00`（语义 "low stock"）已存在，预警标识无需新增令牌。
- 关键信号：数据资产就绪，**无技术阻断**；orders.json 为空仅影响"当前无演示成交量级"，E2E 可通过真实下单+支付链路构造。

## 原始需求信息 (Raw Requirements)

- 运营（库存）：按商品/品类**可配置的低库存阈值**（跑量款高、慢销款低），**售罄前预警**而非售罄后被动。
- 运营（库存）：需要**超卖风险**可视化（库存低于在途/潜在需求时给出标识），避免支付时才失败。
- 运营（补货）：基于销量速度给出**预计售罄天数**与**建议补货量**，权衡断货与资金占用。
- 老板：**全局库存健康度只读总览**（快售罄清单 + 库存资金占用），与销售看板形成经营决策闭环。
- 运营（商品管理）：阈值**低频配置**、**默认值兜底**、复用既有 product-admin 操作习惯，不新增角色。
- 全角色：库存洞察为**只读聚合**，不改变库存/订单语义；展示必须基于**真实数据**。

## 业务约束与规则线索 (Constraints & Rule Clues)

- **阈值口径线索**：判定规则 `stock ≤ 阈值` 商品进入预警列表（ROADMAP Exit Criteria 3 已定）；阈值建议为"件数"整数（非比例/金额），支持**全局默认 + 商品级覆盖**（访谈 1/3 信号，待 explore 确认）。
- **阈值配置生命周期线索**：低频写操作（访谈 3：设一次长期有效）；配置**即时生效**（ROADMAP EC3"阈值配置即时生效"）；配置为 B 端写操作，需明确持久化与生效机制。
- **权限线索**：预警/看板 API 仅 `运营 / 老板` 可访问，`客户 / 客服` 403（对齐 R-DASH-006 与 ROADMAP EC4）；阈值配置仅 `运营` 可写（对齐 Epic 5.1"老板为只读看板角色，无管理写权限"——domain_model 行 ~869）。
- **只读约束**：库存洞察 API 为只读聚合（复用 `aggregateSales`/`buildProductRanking` 同源口径）；阈值配置是本 Epic 唯一写操作，且不触达交易语义。
- **超卖风险线索**：现有 `payment.js` 支付二次校验 `OUT_OF_STOCK` 已兜底；预警需暴露"当前库存 vs 销量速度/在途需求"的风险水位（口径待 explore 确认）。
- **真实数据**：示例必须用现有 6 商品真实数据（极简机械键盘/无线办公鼠标/高清显示器/桌面收纳架/铝合金笔记本支架/桌面拾音氛围灯）+ 真实订单量级，严禁占位符。
- **极简 UI**：slate 色系、无圆角阴影、零第三方图表库（CSS/SVG）；低库存标识直接使用 `--warning`（#FF9A00）语义令牌。
- **治理映射线索**：`data-insights` Bounded Context 新增 `stock-insight` capability（ROADMAP Guardrails 明确 `sales-dashboard` / `stock-insight` 双 capability）；复用 domain_model 行 ~877 前瞻 ReadModel `Operator 库存看板`。

## 疑问与待澄清项 (Open Questions)

1. 阈值粒度：全局单一阈值 vs **全局默认 + 商品级覆盖**？访谈 1 明确要分商品设线，倾向后者，需确认。
2. 阈值配置权限：仅 `运营` 可写、`老板` 只读？（对齐 Epic 5.1 老板只读定位，需确认。）
3. 日均销量窗口：近7日还是近30日？无销量商品（新上架/零成交）售罄天数如何展示（∞ / 不预警 / 隐藏）？
4. 建议补货量口径：MVP 仅 `目标库存 − 当前库存`，还是纳入**到货周期内预计销量**与**安全库存**因子？（ROADMAP 仅要求"预计售罄天数 + 建议补货量"，倾向 MVP 极简口径。）
5. 超卖风险标识口径：候选 = 当前库存 < 日均销量 × 到货周期，或纳入 PENDING_PAYMENT 未支付订单占用量？需业务确认。
6. 阈值默认值：初始默认取多少？（候选：10 件，或按品类差异化默认——需运营确认。）
7. 阈值配置持久化：配置落盘（data/*.json）且即时生效？涉及 B 端写操作落盘机制，需确认。
8. `老板` 角色种子演示账号缺失：是否补充 `user_1003` 老板演示用户，便于 E2E 与演示？（涉及种子数据变更，需确认。）
9. 库存为 0 的商品：在预警列表中以"已售罄"特殊状态展示，还是仅 `stock ≤ 阈值` 且 `stock > 0` 才入列？（需确认售罄商品的可见性。）

## 调研结论 (Research Conclusion)

- **关键发现**：① 低库存预警是运营刚需，阈值需**可配置且支持分商品**（跑量/慢销不同线）；② **超卖风险**是明确担忧，现有支付二次校验只能兜底失败，预警需可视化风险水位；③ 补货决策链 = 销量速度 → 售罄天数 → 建议补货量，且需权衡资金占用；④ 老板需要**全局库存健康度只读视角**，与已交付销售看板闭环；⑤ 阈值配置为**低频 B 端写操作**，需默认值 + 运营权限 + 即时生效。
- **数据可行性**：✅ 数据资产就绪，无技术阻断——`Product.stock` 不变量（`stock≥0`）提供真实库存事实；`items.quantity`（订单快照）+ `paidAt` 可计算销量速度，且 `buildProductRanking`（order.js 行 204）已沉淀商品销量聚合可直接复用；`resolveDashboardRange` 时间换算可复用；`requireRole('运营','老板')` 权限白名单模式已落地；`--warning` 低库存语义令牌已存在。orders.json 当前为空仅影响"当前无演示成交量级"，E2E 经真实下单+支付链路可构造。
- **是否足够支撑进入 explore**：✅ 是。调研信息完整，9 个待澄清项（阈值粒度/口径/权限/默认值/超卖标识/持久化/老板演示账号/售罄可见性）将在 explore 阶段与用户确认后定稿。
