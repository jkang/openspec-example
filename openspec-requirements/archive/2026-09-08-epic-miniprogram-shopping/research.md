## Epic 背景 (Epic Context)

- **Epic 一句话**：小程序 C 端交易链路——商品浏览 / 关键词搜索 / 分类 / 详情、购物车、结算（优惠券最优核销）、模拟支付、我的订单（列表 + 状态轨迹）；完全复用现有 Catalog / Cart / Coupon / Order 后端 API 与数据源，Web 与小程序同库实时一致。
- **所属阶段**：Phase 6 微信小程序渠道（`docs/ROADMAP.md`）。产品理由：目标买家（贸易型中小企业客户）日常活跃于微信，小程序是零安装、低门槛的移动购物入口。
- **前置底座（Epic 6.1 已交付并归档，2026-09-08）**：
  - **渠道配置**：`miniprogram-channel` capability——appid/appsecret（脱敏）/商户号（纯预留）/启用状态；运营可写、老板只读；停用 → `CHANNEL_DISABLED` 拒绝新登录。
  - **微信授权登录**：`wechat-auth` capability——`User.openid` 字段（Q1 方案 A）、code2session 换 openid（mock 网关 Q6）、手机号绑定（撞号提示登录 Q2）、同源账户复用 User/会话。
  - **会话渠道来源**：`Session.channel`（WEB / MINIPROGRAM，wechat-auth 登录 = MINIPROGRAM）→ 下单自动继承写 `Order.channel`（Q7 服务端判定防伪造）。
  - **B 端订单渠道标识**：订单管理列表展示「小程序 / 网页」渠道列。
- **本次调研触发**：6.1 交付了"渠道 + 账户 + channel 底座"，但 **C 端买家尚无法在小程序内完成浏览→下单→支付→追踪的完整旅程**（6.1 仅含登录入口 UI）；6.2 补齐该旅程，兑现"把生意搬进微信"的买家侧闭环。

## 访谈原始记录 (Interview Raw Notes)

> ⚠️ 组成部分（内嵌，非独立文件）：调研过程中的一手原始记录，是后续所有分析的证据来源。访谈为**场景化模拟**。

### 访谈记录 1：林采购（目标买家 / 采购员）
- 时间/方式：2026-09-08 线上访谈（约 20 分钟）
- 原始摘录：
  - "我买东西基本就在微信里：看到哪家店的货，点进去就想直接下单，最好别跳网页。"
  - "选东西的流程跟网页一样就行：搜一下、看分类、点开详情看库存价格，加购物车，结算时自动用上最划算的券，最后微信里付掉。"
  - "付完款我要能马上看到订单到哪一步了——待发货、已发货，能追踪就踏实。"
  - "微信里最怕的就是步骤多，每一步都要简短、点击少。"
- 关键信号：① 完整旅程（浏览→加购→结算→支付→追踪）需在微信内一气呵成；② 交互需**移动端极简**（少步骤、少输入）；③ 结算自动最优券、支付后订单状态可追踪是核心体验点。

### 访谈记录 2：王老板（卖家企业主）
- 时间/方式：2026-09-08 线上访谈（约 15 分钟）
- 原始摘录：
  - "6.1 把渠道和登录打通了，但我真正要的是客户能在微信里把单下下来——小程序里能完整买东西，这个渠道才算活。"
  - "客户在小程序下的单，跟我网页上的单必须是同一批货同一本账，别让我对账对两遍。"
  - "小程序里放真实商品和价格，别搞花架子；客户看得见有货、价格清楚，才敢下单。"
- 关键信号：① **完整下单能力**是渠道"活起来"的标志（6.1 底座的消费场景）；② Web/小程序**同库同账**（复用同一订单池，channel 只是来源标识）；③ 真实数据（6 商品）与价格透明。

### 访谈记录 3：陈运营（B 端运营）
- 时间/方式：2026-09-08 线上访谈（约 15 分钟）
- 原始摘录：
  - "6.1 之后订单列表已经能看出哪单是微信下的了，我这边发货取消都是照常处理，没什么区别。"
  - "只要客户在小程序下单后我能正常看到并处理（发货/取消），微信单跟网页单一样管就行。"
- 关键信号：① B 端**无新增承诺项**——小程序订单处理沿用 6.1 已交付能力（渠道标识列 + 同流程发货/取消）；② 本 Epic 是纯 C 端旅程补充。

### 访谈记录 4：周工（技术负责人）
- 时间/方式：2026-09-08 代码走查（约 30 分钟）
- 原始摘录：

  - "购物车现在是有会话就跟用户走（R-SES-007 之后跟 userId），小程序里微信登录后就是普通会话，直接复用。"
  - "真正要做的是**小程序端 UI 旅程**：商品列表/详情/购物车/结算/支付/我的订单的移动端交互。技术栈（原生 WXML / uni-app / Taro）ROADMAP 说不锁定，由 lead 与 engineer 评估——仓库现有 Vue3 前端与 Playwright E2E 基建，落地形态需要权衡。"
  - "我的订单状态轨迹 UI 在 Web 端已有（待支付→已支付→已发货→已完成 + 已取消），小程序端可复用同套 API 数据语义重新渲染。"
- 关键信号：① **后端零改动**（纯复用，含 channel 继承与购物车归属）；② 增量 = **小程序端 UI 旅程 + 渠道化 E2E**；③ 技术栈形态待决策（移动端 UI 如何落地：原生小程序工程 vs 复用 Vue 栈的可交互移动端视图 + 后端 API 打通，验证闭环需 Playwright 可测）。

## 原始需求信息 (Raw Requirements)

- 买家：微信内完成完整购物旅程（浏览 → 搜索/分类 → 详情 → 加购 → 结算（自动最优券）→ 模拟支付 → 我的订单追踪）；交互移动端极简（少步骤、少输入、真实数据、价格清晰）。
- 卖家/老板：小程序具备**完整下单能力**（6.1 渠道底座"活起来"）；Web 与小程序**同库同账**（同一订单池，channel 仅来源标识）；真实商品与价格。
- 运营：小程序订单处理沿用 6.1 已交付能力（无新增 B 端承诺）；发货/取消与网页单一致。
- 技术：后端 100% 复用；增量聚焦小程序 C 端 UI 旅程与渠道化 E2E 验证。

## 业务约束与规则线索 (Constraints & Rule Clues)

- **渠道门禁（Q5 联动）**：小程序购物旅程依赖渠道启用状态——渠道停用时小程序登录被拒，旅程入口相应不可达（对齐 6.1 CHANNEL_DISABLED 语义）。
- **同源账户（硬约束）**：购物车/订单归属复用既有会话（userId）语义；微信登录用户与网页用户同池，无独立小程序用户池。
- **channel 继承（Q7）**：小程序来源会话下单自动写 `Order.channel=MINIPROGRAM`（服务端判定已落地）；C 端旅程不暴露渠道概念，B 端订单列表可见来源。
- **模拟支付（ROADMAP Guardrails）**：小程序 MVP 复用模拟支付（与 Web 一致），真实微信支付后置 +X；商户号仅配置预留（6.1）。
- **数据与视觉约束**：真实 6 商品数据（极简机械键盘/无线办公鼠标/高清显示器/桌面收纳架/铝合金笔记本支架/桌面拾音氛围灯）、全中文、ZAPP 暗黑令牌、无圆角阴影、移动端极简；**严禁占位符与双端数据不一致**。
- **复用边界（技术）**：后端 API 零改动；前端旅程若以复用 Vue 栈的可交互移动视图落地，需保证与 Web 同源 API/数据一致；若评估引入独立小程序工程（原生/uni-app/Taro），需权衡仓库验证闭环（Playwright E2E）可行性。

## 疑问与待澄清项 (Open Questions)

1. **技术栈落地形态（关键决策，待 explore 确认）**：小程序 C 端旅程以何种形态交付？
   - A) 复用仓库既有 Vue3 + Tailwind 栈，新增**移动端（phone-frame）旅程视图**（与 Web 同源 API，Playwright E2E 可全链路验证）；
   - B) 引入独立小程序工程脚手架（原生 WXML / uni-app / Taro），但仓库无对应构建与 E2E 基建，验证闭环降级；
   - C) 混合：先以 A 交付可验证闭环，原生工程化作为交付后迁移项。
2. **旅程拆分粒度**：按"浏览发现 / 购物车结算支付 / 我的订单"拆 3 Story，还是按单旅程整体交付？（倾向前者，storymap 定稿。）
3. **C 端是否展示渠道**：订单详情/列表是否对 C 端买家展示渠道来源？（倾向不展示——channel 是内部/B 端语义，C 端不感知，需确认。）
4. **微信内分享/转发**：是否含小程序分享（商品卡片转发）？（ROADMAP 未提，倾向 MVP 不含。）
5. **收货信息/地址**：结算是否需要收货地址？（现系统无地址模型——Web 端也未含，倾向 MVP 复用"无地址模拟订单"现状，需确认。）

## 调研结论 (Research Conclusion)

- **关键发现**：① 买家需要微信内**一气呵成的完整购物旅程**（浏览→下单→支付→追踪），交互移动端极简；② 后端 **100% 复用**（6.1 已备好 channel 继承/会话归属/模拟支付/我的订单 API），本 Epic 是纯 **C 端旅程补充**（B 端无新增承诺）；③ Web/小程序同库同账、channel 仅来源标识；④ 技术栈落地形态是**唯一关键技术决策**（移动端 UI 如何交付且保持仓库可验证闭环）。
- **数据可行性**：✅ 后端零改动即可支撑完整旅程；既有 Playwright + Cucumber E2E 基建（Vue 5173 + Node 3000）可全链路验证小程序旅程（微信登录 → 浏览 → 加购 → 结算 → 支付 → 我的订单），断言 channel=MINIPROGRAM 落单。
- **是否足够支撑进入 explore**：✅ 是。调研信息完整；关键技术决策（落地形态 A/B/C）与 5 个待澄清项将在 explore 阶段呈报用户确认后定稿。
