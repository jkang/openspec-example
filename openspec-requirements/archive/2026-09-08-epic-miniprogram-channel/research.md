## Epic 背景 (Epic Context)

- **Epic 一句话**：小程序渠道接入与账户打通——B 端小程序渠道配置（appid / appsecret / 商户号 / 启用状态，仅运营角色）+ 微信授权登录（openid）→ 手机号绑定 → 复用现有 User 账户/会话体系（同源账户）+ B 端订单管理展示渠道标识（`channel=MINIPROGRAM`），小程序订单可正常发货/取消。
- **所属阶段**：Phase 6 微信小程序渠道（`docs/ROADMAP.md` 未来 +1 个月，**当前启动阶段**）。产品理由：目标买家（贸易型中小企业客户）日常活跃于微信，小程序是零安装、低门槛的移动购物入口，直接承接"订单散落在表格、回款在群聊"痛点中买家侧的数字化下单诉求。
- **触发条件**：Phase 5 Exit Criteria 已全达成（含 Epic 5.2 库存预警交付）✅ 可启动。Epic 6.1 是 **6.2 的前置**——先打通渠道配置与同源账户，6.2（小程序 C 端购物链路）才可在 `channel=MINIPROGRAM` 标识与微信登录之上复用既有 Catalog/Cart/Coupon/Order API。
- **前置现状（代码审计结论，2026-09-08）**：
  - **当前代码库不存在任何小程序/渠道概念**：全仓 grep `channel / openid / wechat / appid / mini` 无业务命中（仅前端 `formatMoney` 注释含 "mini" 无关命中；`fileRepo.js` 的 "data" 为目录语义）。
  - 认证体系为**手机号 + 密码**单一登录因子：`User` 实体（`src/domain/types.js`）字段 `id/phone/passwordHash/nickname/status/role/createdAt`，`phone` 11 位中国大陆手机号**全局唯一**（R-REG-002）；登录路由仅 `/api/auth/register|login|logout`（`server.js` 行 648-675）。
  - 会话体系为**服务端 token→userId 映射**（Session 实体，`user-session` capability），登录/注册创建，退出销毁，禁用即失效（R-SES-001~006）——**小程序登录预期复用该会话底座**。
  - `Order` 实体（`types.js`）字段无渠道来源：`id/status/totalCents/discountCents/actualPaidCents/couponId/items/userId/createdAt/paidAt`；B 端订单管理（`GET /api/admin/orders` + 发货/取消）已落地。
  - B 端权限门禁模式成熟：`requireRole('运营')` / `requireRole('运营','老板')`（`server.js`，R-ADM / R-DASH-006）——渠道配置权限可复用同一白名单门禁基建。
  - 角色模型：`客户 / 运营 / 客服 / 老板`（`types.js` User.role；R-ADM 门禁仅运营可管用户；老板只读看板）。
  - 种子用户：`user_1001 陈晓芸（运营）` / `user_1002（客户）` / `user_1003（老板）`（`server.js` initialUsers / `data/users.json`）。

## 访谈原始记录 (Interview Raw Notes)

> ⚠️ 组成部分（内嵌，非独立文件）：调研过程中的一手原始记录，是后续所有分析的证据来源。访谈为**场景化模拟**，原始摘录基于画像与真实平台机制构造。

### 访谈记录 1：王老板（贸易型中小企业老板 / 决策者）
- 时间/方式：2026-09-08 线上语音访谈（约 25 分钟）
- 原始摘录：
  - "我的客户都是微信里的老熟人，他们习惯微信里直接下单、直接催单。现在让他们开电脑上网页买，太麻烦，好几单就是这么丢的。"
  - "渠道到底是不是真的能用、什么时候能收钱，我得能看见、能关掉——万一商户号没办下来，别让小程序摆在那误导客户下单。"
  - "我担心以后微信里下的单和网页下的单变两本账。客户是同一批人，账户必须是一套，不能让客户在小程序里还要重新注册一遍。"
  - "商户资质、appsecret 这些是敏感的东西，最好只有运营能配，别让客服也能动。"
- 关键信号：① 微信是买家高频触点，**渠道必须真实可用且可开关**（启用状态可见可控）；② **同源账户**是硬诉求（复用现有 User，不建独立用户池）；③ 渠道配置是**敏感 B 端写操作**，权限需收敛到运营。

### 访谈记录 2：陈运营（B 端运营）
- 时间/方式：2026-09-08 线上访谈（约 30 分钟）
- 原始摘录：
  - "如果开通了小程序渠道，订单列表里我得能一眼看出这单是微信里下的还是网页下的，不然客户打电话来问单子，我连他是在哪儿下的都不知道。"
  - "配 appid、商户号这种事不常做，但配完得让我确认生效了；配错了要能改，关掉渠道要能立刻停。"
  - "小程序下的单发不发货、能不能取消，跟网页单应该一样处理，别搞两套流程。"
  - "手机号绑定最怕撞号：客户在网页已经注册过，微信里又授权一遍，系统得认得是同一个人，不能建个新号把历史订单弄丢了。"
- 关键信号：① B 端订单管理需**渠道来源标识**（列表可见），处理流程（发货/取消）与网页单一致；② 渠道配置需**生效可见 + 可停用**；③ **手机号绑定需防撞号/防重复建户**（同源账户与既有 `phone` 全局唯一的衔接）。

### 访谈记录 3：林采购（目标买家代表 / 采购员）
- 时间/方式：2026-09-08 线上访谈（约 20 分钟）
- 原始摘录：
  - "微信里买东西，最烦还要注册账号输密码。最好点一下微信授权就直接能用，别让我填手机号密码。"
  - "下单、看物流最好都在微信里完成，跟聊天记录放一起，方便翻。"
  - "如果我以前在网页买过，微信里再进来，得让我能看到我以前的订单，不然以为系统把我数据弄丢了。"
- 关键信号：① 登录**极简优先**：期望微信授权（openid）即登录，减少表单；② C 端旅程集中在微信生态内；③ 老客户跨端（网页→小程序）需**订单延续可见**（同源账户的直接收益）。

### 访谈记录 4：周工（技术负责人）
- 时间/方式：2026-09-08 代码走查 + 平台机制核查（约 40 分钟）
- 原始摘录：
  - "现在认证只有手机号+密码一条路，User 表没有 openid 字段；要做微信登录就得给 User 增加微信身份关联，或者建 openid→User 的映射，不能破坏手机号唯一这条既有约束。"
  - "微信登录的真实链路是：小程序端 `wx.login()` 拿 code → 服务端拿 appid+appsecret 调 `code2session` 换 openid。openid 是**按 appid 隔离**的，同一个人在我们这个小程序里是一个固定 openid。注意不能把 appsecret 发到前端，必须服务端持有。"
  - "小程序里拿手机号要用官方的『手机号快速验证组件』，用户在微信里点授权，我们拿到的是加密数据/code，服务端解密换手机号——不是直接表单填。真机与模拟环境行为不一样，本仓库零第三方依赖 + 测试要可复现，得考虑 mock 微信网关的测试策略。"
  - "真实微信支付要企业主体认证 + 商户号（mchid）+ appid 与商户号绑定 + API 证书，资质门槛高。ROADMAP 说 MVP 保持模拟支付，那商户号字段本期应该只是**配置预留**，真实支付留到交付后评估。"
  - "存储方面 appsecret 是敏感项，现在 JSON 明文落盘风格对普通业务数据没问题，但 appsecret 这种凭证不建议明文落盘，至少要考虑脱敏回显（写入不回读明文）。"
- 关键信号：① **技术链路明确**：openid（code2session 服务端换取）是登录因子，需服务端持有 appsecret、设计 openid↔User 关联；② **手机号获取走微信组件**而非表单；③ **商户号 = 配置预留**（模拟支付 MVP，真实支付资质后置）；④ 测试需 mock 微信网关；⑤ **appsecret 敏感存储**需脱敏回显。

## 原始需求信息 (Raw Requirements)

- 老板：小程序渠道可**启用/停用**、状态可见；渠道配置（appid/appsecret/商户号）仅**运营**可维护；渠道不可用时不得误导客户下单。
- 老板/运营：**同源账户**——小程序登录复用现有 User 账户/会话，微信用户与网页用户是同一账户体系（不做独立用户池、不重复注册）。
- 买家：**微信授权即登录**（openid 一键授权，减少手机号密码表单）；老客户跨端（网页→小程序）订单延续可见。
- 运营：B 端订单列表需展示**渠道来源**（`channel=MINIPROGRAM`）；小程序订单发货/取消与网页单同流程。
- 技术：微信登录走官方 code2session 链路（openid 为登录因子，服务端持有 appsecret）；手机号绑定采用微信官方获取能力；appsecret 敏感存储；真实微信支付资质后置（本期商户号配置预留）。
- 全角色：保持现有极简约束与角色权限门禁（客户/客服不可见渠道配置，仅运营可写）。

## 业务约束与规则线索 (Constraints & Rule Clues)

- **同源账户（硬约束，ROADMAP Guardrails）**：小程序用户与 Web 用户同一 `User` 表，openid/手机号只是**新的登录因子**，不做数据孤岛；严禁因渠道引入第二套用户池。
- **手机号唯一约束衔接**：既有 `User.phone` 11 位大陆手机号**全局唯一**（R-REG-002）；微信绑定手机号必须与该约束衔接——已存在同手机号用户时不能新建重复户（防撞号，访谈 2 信号）。
- **登录/会话复用**：会话体系为服务端 token→userId（`user-session` capability）；微信授权登录预期复用会话创建能力，避免旁路建会话（对齐 R-SES-001~006 与禁用即失效）。
- **权限门禁（对齐既有模式）**：渠道配置为 B 端写操作，仅 `role=运营`（对齐 `requireRole` 白名单基建与 R-ADM 家族）；`客服 / 老板 / 客户 / 未登录` 无权写。ROADMAP Guardrails 明确"扩展 R-ADM 权限门禁"。
- **模拟支付边界（ROADMAP Guardrails）**：MVP 保持模拟支付（与 Web 端一致）；真实微信支付（商户资质/证书）为交付后 +X 评估项——因此**商户号（mchid）本期为配置预留**，不接入真实支付回调。
- **微信平台技术约束（官方机制）**：
  - openid 为**按小程序 appid 隔离**的用户身份；服务端通过 `wx.login()` code + appid + appsecret 调 `code2session` 换取（appsecret **严禁下发前端**）。
  - 小程序内获取手机号走官方**手机号快速验证组件**（用户点授权），服务端解密/code 换取——非表单填写。
  - 真实交易需商户号与 appid **绑定** + API 证书/密钥（商户平台配置），本期不落地。
- **敏感凭证存储**：appsecret 等凭证建议**写入不回显明文**（脱敏/掩码），不沿用普通业务 JSON 明文回显风格（访谈 4 信号，口径待 explore 确认）。
- **测试可复现**：微信网关（code2session / 手机号组件）无法在本地真实验证，需设计 mock 网关策略保证 E2E 可复现（既有 `NODE_ENV=test` 测试后门 `__test/*` 模式可参考）。
- **渠道标识字段**：Order 增加渠道来源（`channel=MINIPROGRAM`，默认 WEB）以支撑 B 端订单管理标识与后续 Epic 6.2 旅程；不改动既有订单语义/状态机。
- **治理映射线索（ROADMAP Guardrails）**：User Context 新增 `wechat-auth` capability；新增 `Channel Context` BC 与 `miniprogram-channel` capability；Order 增加渠道来源字段；`domain_model.html` / `service_blueprint.html` 显式标注"新增"。
- **极简与真实数据（全阶段约束）**：无圆角阴影、ZAPP 设计令牌、中文、真实业务数据示例（6 商品：极简机械键盘等）；小程序技术栈（原生 WXML / uni-app / Taro）由 lead 与 engineer 评估后定，roadmap 不锁定。

## 疑问与待澄清项 (Open Questions)

1. **openid 关联模型**：✅ **已确认（2026-09-08 HITL）：方案 A——`User` 增加 `openid` 字段**（一人一小程序一 openid，一对一）。本 Epic 为单小程序场景，MVP 不做独立映射表。
2. **绑定时序与撞号处理**：✅ **已确认（2026-09-08 HITL）：绑定时若该手机号已被既有账号占用，提示登录既有账号再绑定**（不自动合并、不静默拒绝）。微信授权后是否必须绑手机号才能下单的时序留待 explore 按同源账户规则定稿。
3. **商户号字段本期语义**：✅ **已确认（2026-09-08 HITL）：纯配置预留**——本期不校验资质、不参与支付、不接入真实回调（模拟支付 MVP，真实微信支付资质后置 +X）。
4. **appsecret 存储策略**：✅ **已确认（2026-09-08 HITL）：写入后回显脱敏**（显示掩码 + 「已配置」标记，不读回明文），支持重新配置覆盖。
5. **渠道配置启用状态的生命周期**：停用渠道后，既有小程序会话是否失效、下单入口是否立即隐藏？待 explore 细化（老板"可关停"诉求落地为渠道门禁/展示联动）。
6. **mock 微信网关策略**：✅ **已确认（2026-09-08 HITL）：设计 mock 微信网关对齐既有 `NODE_ENV=test` 测试后门模式**（固定 code→openid 映射或后门接口），保证 E2E 可复现。
7. **渠道标识展示粒度**：B 端订单管理仅"列表显示渠道来源"，还是需要按渠道筛选/统计？（ROADMAP 仅要求"展示订单渠道标识"，MVP 倾向仅展示，待 explore 确认。）
8. **前端触点归属**：✅ **已确认（2026-09-08 HITL）：Epic 6.1 包含小程序端登录入口 UI**（渠道接入与账户打通的 C 端触点随 6.1 交付：微信授权登录/手机号绑定页）；6.2 再承载完整购物旅程（浏览/加购/结算/我的订单 UI）。
9. **`wechat-auth` 与既有 `account-management`/`user-session` 的边界**：新增 capability 承载"微信授权登录因子"，与既有注册/登录/会话能力如何划分（复用会话创建 vs 新增登录编排）？待 explore 按 domain_model 映射定稿。
10. **UnionID 是否需要**：单小程序场景 openid 已够用；倾向 MVP 不引入 unionid（非目标清单未提），待 explore 确认。

## 调研结论 (Research Conclusion)

- **关键发现**：① 微信渠道是承接"买家侧数字化下单"的真实触点，老板明确要求渠道**可用可停、配置收敛运营权限**；② **同源账户**为全角色共识（复用 User，不做独立用户池），其技术落点是"新增 openid 登录因子 + 与既有手机号唯一约束/会话底座衔接"；③ B 端订单管理需**渠道来源标识**且处理流程与网页单一致；④ 技术链路清晰：`wx.login()` code → 服务端 `code2session` 换 openid（appsecret 服务端持有），手机号经官方组件获取，**商户号本期仅配置预留**（真实支付资质后置）；⑤ 存储/测试存在真实约束：appsecret 敏感脱敏、微信网关需 mock 保 E2E 可复现。
- **数据可行性**：✅ 现有 `User`（phone 唯一、status/role）、`Session`（token→userId）、`Order`（可增 `channel` 字段）、`requireRole` 权限门禁与文件/内存仓储均**可直接复用**；`user-session` / `account-management` / `user-admin` capability 提供既有登录/会话/B 端管理底座。无技术阻断，增量聚焦"新增微信身份因子 + 渠道配置 + 渠道标识"三块。
